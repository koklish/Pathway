# Занятость дисков в сайдбаре вместо меток

## Цель

Секция «Метки» в сайдбаре декоративна: семь цветных кружков, клик по которым
ничего не делает (`SidebarView.SidebarRow` — `case .place, .tag, .network:
break`). Поиска по меткам в приложении нет, и появиться ему неоткуда — это
отдельная задача поверх Spotlight.

Место занимает восемь строк постоянно. Вместо них — секция «ДИСКИ»: сколько
занято на каждом смонтированном томе, полоской заполнения и цифрами. Показ
включает загрузочный диск, внешние и сетевые тома.

## Архитектура

### `Sources/PathwayCore/VolumeUsage.swift` (новый)

```swift
public struct VolumeUsage: Identifiable, Equatable, Sendable {
    public var id: String { url.path }
    public let url: URL
    public let name: String
    public let isNetwork: Bool
    public let totalBytes: Int64
    public let availableBytes: Int64

    public var usedBytes: Int64 { max(0, totalBytes - availableBytes) }
    public var fraction: Double        // 0…1, при totalBytes == 0 → 0
    public var caption: String         // «Свободно 653 ГБ из 926 ГБ»
}

public protocol VolumeUsageReading: Sendable {
    func read() -> [VolumeUsage]
}

public struct VolumeUsageReader: VolumeUsageReading { ... }
```

Протокол — по правилу проекта о границах с ОС: чтение томов зависит от того,
что смонтировано на машине в момент прогона, и без подмены секция проверялась
бы только глазами.

Занятое считается как `total - available`, а не берётся напрямую. На APFS
загрузочный том разложен на несколько контейнеров с общим пулом: `/` отдаёт
занято 13 ГБ, тогда как реально израсходовано около 273 ГБ — они лежат в
`/System/Volumes/Data`. Свободное место у обоих контейнеров общее и честное.

Отбор томов: `mountedVolumeURLs(includingResourceValuesForKeys:options:)` со
`.skipHiddenVolumes`, плюс явный отброс путей внутри `/System/Volumes` и всего,
что не `/` и не в `/Volumes`. `df` показывает десяток служебных точек (`devfs`,
`/System/Volumes/VM`, `Preboot`, `Update`, `xarts`), и без фильтра секция
состояла бы в основном из них.

Ключи ресурсов: `.volumeTotalCapacityKey`, `.volumeAvailableCapacityKey`,
`.volumeNameKey`, `.volumeIsLocalKey`. Для важного объёма годится
`.volumeAvailableCapacityForImportantUsageKey`, но он на сетевых томах часто
nil, а разные источники у локальных и сетевых дали бы несравнимые полоски.

### `Sources/PathwayCore/SidebarModel.swift`

`tags()` и `SidebarItem.TagColor` удаляются; `Kind.tag` тоже — единственный его
потребитель во вью уходит вместе с секцией. `buildSections` оставляет одну
секцию «МЕСТА».

Секция дисков не строится здесь: у неё своё обновление по таймеру, и ей нужен
не `SidebarItem`, а `VolumeUsage` с числами. Модель секции — отдельный
`@Observable VolumesModel` в том же файле или рядом:

```swift
@Observable @MainActor
public final class VolumesModel {
    public private(set) var volumes: [VolumeUsage] = []
    public init(reader: any VolumeUsageReading = VolumeUsageReader())
    public func refresh()
}
```

`refresh()` синхронный: чтение — вызов `statfs` под капотом, счёт идёт на
микросекунды даже для сетевого тома (данные уже в таблице монтирования).
Обхода каталогов здесь нет, и `Task.detached` был бы усложнением без выигрыша.

### `Sources/Pathway/SidebarView.swift`

Секция «ДИСКИ» рисуется после «Сети». `SidebarRow` теряет ветку `.tag`, вместе
с ней уходит `Color(tag:)` и его `init`.

Строка тома: иконка (`internaldrive` для локального, `externaldrive.connected.
to.line.below` для сетевого), название, полоска `Capsule` с заливкой по
`fraction`, подпись вторичным цветом. Клик ведёт в корень тома — в отличие от
меток, у диска есть куда вести.

Полоска красная при заполнении выше 90 %: место кончается, и цвет — то, что
замечают, не читая цифр. Порог в Core (`VolumeUsage.isNearlyFull`), а не во
вью: это правило, а не оформление.

Обновление: `refresh()` на появлении сайдбара и по таймеру раз в 30 секунд.
Занятость меняется постоянно, а событие «место кончилось» — редкое; опрос
чаще нагружал бы сетевые тома запросами ради цифры, на которую никто не смотрит.

## Поток данных

```
Таймер 30 с / .onAppear
  → VolumesModel.refresh()
  → VolumeUsageReader.read()
      mountedVolumeURLs → отброс служебных → resourceValues
  → [VolumeUsage]
  → SidebarView: секция «ДИСКИ», строка на том
  → клик → model.navigate(to: url)
```

## Тесты

`Tests/PathwayCoreTests/VolumeUsageTests.swift`:

- доля занятого: 294 ГБ всего, 79 ГБ свободно → 0.73
- нулевой объём тома даёт долю 0, а не NaN (FTP-том отдаёт нули, и NaN уронил
  бы отрисовку полоски)
- свободное больше общего (сервер соврал) не даёт отрицательного занятого
- подпись содержит и свободное, и общее
- порог «почти заполнен» срабатывает выше 90 %, а на 90 % ещё нет

`Tests/PathwayCoreTests/VolumesModelTests.swift` с `InMemoryVolumeUsageReader`:

- `refresh()` заполняет список тем, что отдал читатель
- повторный `refresh()` заменяет список, а не добавляет к нему
- пустой ответ читателя даёт пустой список, а не оставляет прошлый

`SidebarModelTests` правится: секций теперь одна, проверка меток удаляется.

## Ручной чек-лист

- [ ] Секции «МЕТКИ» в сайдбаре нет
- [ ] Секция «ДИСКИ» показывает Macintosh HD, «Спецификации», MAIN и FTP-том
- [ ] Служебных томов (`/System/Volumes/VM`, `Preboot`, `devfs`) в списке нет
- [ ] Занятое на Macintosh HD близко к тому, что показывает «Об этом Mac», а не
      13 ГБ
- [ ] Клик по тому открывает его корень в списке файлов
- [ ] Отключение сетевого тома убирает его из секции в течение 30 секунд

## Вне рамок

- **Поиск по меткам вместо удаления секции.** Отдельная задача поверх Spotlight
  с собственной спекой; сейчас секция не работает вовсе, и держать неработающее
  ради возможного будущего незачем.
- **Показ занятости в статусной строке.** Там место занято счётчиком папок и
  файлов, и он относится к текущей папке, а не к тому.
- **Кнопка извлечения тома.** Управление подключением живёт в секции «Сеть», и
  второе место для того же действия развело бы их поведение.
- **Обновление по событию монтирования (`NSWorkspace.didMountNotification`).**
  Заметило бы подключение мгновенно, но не изменение занятости — а именно оно
  главное в секции. Таймер покрывает оба случая одним механизмом.
