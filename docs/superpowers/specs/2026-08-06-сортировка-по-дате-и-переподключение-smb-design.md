# Сортировка по дате и переподключение SMB после сна

## Цель

Две независимые доработки по отзывам коллег.

**Первая.** Список файлов должен по умолчанию сортироваться по дате, свежие сверху, и этот выбор не должен теряться — ни при переходе между папками, ни при открытии новой вкладки, ни при перезапуске приложения.

Сегодня умолчание — имя по возрастанию (`BrowserModel.sortKey = "name"`), а выбранная сортировка живёт в `BrowserModel` и потому своя у каждой вкладки и не переживает перезапуск.

**Вторая.** После сна компьютера SMB-том отваливается, и приложение больше не может к нему подключиться. Причина в том, что `MountedServers.refresh()` считает том живым по `FileManager.fileExists` на точке монтирования, а отвалившийся том остаётся в таблице монтирования: `isMounted` возвращает true, переподключение не запускается, а обращение к папке виснет на таймауте.

## Архитектура

### Сортировка по дате изменения

Отдельного поля «дата создания» нет намеренно. Создание файла — тоже изменение,
и на практике две даты совпадают у подавляющего большинства файлов; на SMB даты
создания к тому же часто нет вовсе. Заводить ради этого поле в `FileItem`, ключ
в `DirectoryLoader` и пятую колонку в списке — плата, которая не окупается.

Сортировка идёт по существующему `modificationDate`, умолчанием становится уже
имеющийся ключ `"modified"`.

### Порядок «свежие сверху» — это `ascending == false`

Дата по возрастанию — это старые сверху. Умолчание задаётся парой (`"modified"`,
`ascending: false`), а не одним ключом.

Отсюда следствие для UI: прототип дескриптора у колонки даты создаётся с
`ascending: false`, иначе первый клик по её заголовку дал бы «старые сверху» —
обратное тому, что пользователь ждёт от колонки с датой. `NSTableView` берёт
направление первого клика из `sortDescriptorPrototype`.

### Сортировка до прихода метаданных

Первый проход `loadNames` дат не читает вовсе — у всех записей
`metadataLoaded == false`. При сортировке по дате это значит, что список сначала
отрисуется в порядке «все даты равны», а после второго прохода переупорядочится
целиком: строки прыгнут под курсором.

Решение: **пока метаданные не прочитаны, список сортируется по имени,
независимо от выбранного ключа.** В `sorted(_:)` — ранняя ветка: если ни у одной
записи нет метаданных, сравниваем по имени.

Альтернатива «показывать пустой список до второго прохода» отвергнута: она
стоила бы ровно того, ради чего трёхступенчатая загрузка и сделана —
мгновенного появления имён на медленном сетевом диске.

Прыжок строк этим не устраняется полностью — он превращается из «случайный
порядок → правильный» в «по имени → по дате», но становится осмысленным: первый
список отсортирован понятным пользователю образом, а не порядком выдачи readdir.

### Хранение сортировки: глобально и между запусками

Сортировка переезжает из `BrowserModel` в `TabsModel` — туда же, где уже живёт `showHiddenFiles`, и по той же причине: **два хранилища одного флага разошлись бы при первом открытии вкладки.**

- `TabsModel.sortKey` / `sortAscending` — источник правды, при изменении раздаются всем вкладкам, как это уже делает `showHiddenFiles` в своём `didSet`.
- `BrowserModel.sortKey` / `sortAscending` остаются, но становятся ведомыми: их выставляет `TabsModel`, а `BrowserModel.sort(by:ascending:)` вызывается уже через него.
- Новая вкладка создаётся с текущей сортировкой — параметром конструктора `TabState`, рядом с `showHiddenFiles`.
- `AppState.sortKey` / `sortAscending` — проброс к `TabsModel`, по образцу `AppState.showHiddenFiles`.

Персистентность — в `Sources/PathwayCore/TabsStore.swift`, рядом с составом вкладок: ключи `sort.key` и `sort.ascending`. Отдельного стора не заводим — `TabsStore` уже владеет `UserDefaults` и уже хранит настройки сессии вкладок.

**Умолчание при отсутствии сохранённого значения — («modified», false).** `UserDefaults.bool` возвращает false для отсутствующего ключа, что здесь случайно совпадает с нужным `ascending: false`; полагаться на совпадение нельзя — читаем через `object(forKey:)` и подставляем умолчание явно, иначе смысл «ключа нет» и «пользователь выбрал по возрастанию» стал бы неразличим.

### Залипший том: определение

`Sources/PathwayCore/MountedServers.swift`. Проверка `FileManager.fileExists` заменяется на проверку с таймаутом, потому что **обращение к отвалившемуся SMB-тому не возвращает ошибку, а виснет** — на десятки секунд, до истечения системного таймаута. Проверка на главном потоке заморозила бы окно.

Новый метод `probe(_ mountPoint: URL) async -> Bool`: `statfs` на точке монтирования в `Task.detached`, с гонкой против таймаута в 2 секунды. `statfs`, а не `fileExists`: он отдаёт флаги файловой системы и на живом томе возвращается мгновенно, а на залипшем — виснет, что и служит признаком.

Таймаут именно 2 секунды: живой SMB-том в локальной сети отвечает за единицы миллисекунд, а порог должен пережить кратковременную загрузку сети, не заставляя пользователя ждать.

Признак «залип» — не мгновенная ошибка, а именно истечение таймаута: том, которого нет в таблице монтирования, — это обычное отключение, оно уже обрабатывается существующей логикой.

### Залипший том: переподключение

Новый метод `ServerConnection.reconnectStaleVolumes() async` — по одному шагу:

1. Опросить точки монтирования учтённых томов через `probe`.
2. Для залипших — принудительно отключить: `unmount` с флагом `MNT_FORCE`. Обычный `unmountAndEjectDevice` на залипшем томе сам виснет, поэтому нужен форсированный путь; `Mounting` получает второй метод `forceUnmount(_:)`, чтобы тесты по-прежнему не ходили в сеть.
3. Забыть точку монтирования (`mounted.forget`).
4. Смонтировать заново теми же учётными данными, что и при обычном подключении, — переиспользуя существующий `connect(to:)`, а не дублируя выбор пароля.

**Если переподключиться не удалось — том остаётся отключённым, ошибка не показывается.** Причина в сценарии: ноутбук, открытый дома без VPN, встречал бы пользователя алертом каждое утро, хотя ничего не сломано — сервер просто недоступен. Сервер при этом остаётся в сайдбаре как отключённый, и клик по нему запускает обычное подключение со всеми диалогами.

Форсированное отключение делается **в любом случае**, даже когда переподключение заведомо не выйдет: залипший том, оставленный в системе, продолжит вешать приложение при каждом обращении к нему — именно на это и жалуются коллеги.

### Сигнал пробуждения

`Sources/Pathway/MainWindow.swift`: подписка на `NSWorkspace.didWakeNotification` — она приходит из `NSWorkspace.shared.notificationCenter`, а не из `NotificationCenter.default`. Ошибиться здесь легко, и подписка на дефолтный центр молча никогда не сработает.

Обработчик зовёт `connection.reconnectStaleVolumes()`, а следом — уже существующие `resumeWatching()` и `refreshAfterReturn()`, чтобы открытая на сетевом томе вкладка перечитала папку по восстановленному соединению.

Существующая подписка на `didBecomeActiveNotification` остаётся и продолжает звать `mounted.refresh()`: пробуждение и возврат в приложение — разные события, и том могли отключить в Finder без всякого сна.

## Поток данных

**Сортировка.** Старт: `TabsStore.restore()` отдаёт (`sortKey`, `sortAscending`) → `TabsModel` раздаёт их каждой создаваемой `TabState` → `BrowserModel.sorted(_:)` применяет при каждой загрузке. Клик по заголовку: `FileListView.Coordinator.sortDescriptorsDidChange` → `AppState.sort(by:ascending:)` → `TabsModel` (сохраняет в `TabsStore` и раздаёт всем вкладкам) → каждая `BrowserModel` пересортировывает свой список.

**Переподключение.** `NSWorkspace.didWakeNotification` → `ServerConnection.reconnectStaleVolumes()` → для каждой учтённой точки `MountedServers.probe` → залипшие: `forceUnmount` → `mounted.forget` → `connect(to:)` с сохранённым паролем → при успехе `mounted.remember`, при неудаче ничего.

## Тесты

`PathwayCoreTests`, все — на Core.

**Сортировка (`BrowserModelTests` или новый `SortingTests`):**
- сортирует по дате изменения, свежие сверху
- файл без даты уходит вниз, а не ломает порядок остальных
- папки остаются выше файлов при сортировке по дате
- до прихода метаданных сортирует по имени, а не по пустым датам
- смена сортировки в одной вкладке меняет её во всех
- новая вкладка открывается с текущей сортировкой, а не с сортировкой по умолчанию

**Хранение (`TabsStoreTests`):**
- сохранённая сортировка восстанавливается после перезапуска
- при отсутствии сохранённого значения умолчание — дата изменения по убыванию
- `ascending: true`, сохранённый явно, отличим от отсутствующего ключа

**Переподключение (`ServerConnectionTests`, через фейковый `Mounting`):**
- залипший том принудительно отключается и монтируется заново
- живой том не трогается вовсе
- неудачное переподключение оставляет том отключённым и не рождает текста ошибки
- залипший том отключается принудительно даже тогда, когда переподключение не удалось
- переподключение берёт сохранённый пароль, а не спрашивает заново

Фейку `Mounting` добавляется счётчик `forceUnmountCount` — иначе «отключился принудительно» проверить нечем.

## Ручной чек-лист

1. Запустить, убедиться: список отсортирован по дате изменения, свежие сверху.
2. Перейти в другую папку, вернуться — сортировка та же.
3. Открыть новую вкладку — сортировка та же.
4. Кликнуть по заголовку «Имя», перезапустить приложение — сортировка осталась по имени.
5. Вернуть сортировку по дате, перезапустить — осталась по дате.
6. Открыть папку на SMB: список не прыгает после дочитывания метаданных сильнее, чем «по имени → по дате».
7. Подключить SMB-том, усыпить компьютер на несколько минут, разбудить — том переподключился сам, папка открывается без зависания.
8. То же, но отключив Wi-Fi перед пробуждением: том пропал из подключённых, алерта нет, приложение не виснет.
9. После пункта 8 включить сеть и кликнуть по серверу — обычное подключение работает.

## Вне рамок

- **Сортировка отдельно для каждой папки.** Выбрано глобальное умолчание; папочное потребовало бы хранилища «путь → сортировка» с вопросом, когда его чистить.
- **Отдельная колонка «Дата создания».** Создание — тоже изменение, даты совпадают почти всегда, а на SMB даты создания часто нет вовсе: поле, ключ загрузки и пятая колонка себя не окупают.
- **Периодическая проверка залипших томов по таймеру.** Пробуждение и возврат в приложение покрывают жалобу; опрос по таймеру держал бы соединение с сервером и стоил бы сетевых запросов на холостом ходу.
- **Переподключение по клику на залипшую папку.** Выбран сценарий «автоматически при пробуждении»; страховка при обращении — отдельная доработка, если пробуждения окажется мало.
- **Диалог входа при автоматическом переподключении.** Решено отключать тихо: алерт на каждом открытии ноутбука вне офиса раздражал бы сильнее проблемы.
