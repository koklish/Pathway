# Переключение веток

## Цель

Чип показывает ветку, но сменить её нельзя — за этим приходится идти в
терминал. Добавляем два пути: пять недавних веток прямо в подменю (возврат
на вчерашнюю ветку одним кликом) и форму со списком, поиском и серверными
ветками — для всего остального.

## Что выяснено опытом

Поведение git проверено на настоящих репозиториях, и оно определило
конструкцию — поэтому записано здесь, а не выведено из документации.

| Ситуация | Что делает git |
|---|---|
| Правки есть, целевая ветка их не трогает | Переключается и переносит правки с собой |
| Правки конфликтуют с целевой веткой | Отказывается, остаётся на месте, ничего не теряет |
| `switch --track origin/X` | Создаёт локальную `X` и сразу ставит upstream |
| Список 75 веток (`srm`) | 16 мс |

**Отсюда главное: переключение при незакоммиченных изменениях не
блокируется.** Начал править, понял, что не на той ветке, переключился
вместе с правками — ежедневная практика. Запрет сделал бы Проводник строже
самого git.

Своей проверки «дерево грязное» нет и не будет: она назвала бы виноватыми
все правки, включая безобидные, тогда как git знает точно, какие файлы
мешают. Наше дело — показать его отказ понятным текстом.

16 мс на список означают, что кэша и предзагрузки не нужно: ветки читаются
при открытии формы.

## Архитектура

### Список веток — `Sources/PathwayCore/BranchList.swift`

```swift
public struct Branch: Equatable, Sendable, Identifiable {
    public var id: String { name }
    public let name: String          // feature/SDLC/35
    public let isRemote: Bool        // лежит только на сервере
    public let isCurrent: Bool
    public let date: Date?           // последний коммит
}

public enum BranchList {
    static func parse(_ output: String, current: String?) -> [Branch]
}
```

`parse` — чистая функция, тестируется без git. Разбирает вывод
`for-each-ref` с разделителем `|`.

Команда: `git for-each-ref --format=%(refname:short)|%(committerdate:unix)|%(symref)
refs/heads refs/remotes --sort=-committerdate`.

Три решения в разборе:

- **`refs/heads` и `refs/remotes` одним вызовом**, а не двумя: два процесса
  ради разделения, которое видно по префиксу `origin/`, — лишняя цена.
- **Записи с непустым `symref` отбрасываются.** Это `origin/HEAD` —
  указатель на ветку по умолчанию, а не ветка; переключение на него дало бы
  отделённую голову. Отсев именно по `symref`, а не по имени: в выводе
  `for-each-ref` эта запись сокращается до **`origin`**, без `/HEAD`, и
  проверка по строке `origin/HEAD` её не поймала бы. Проверено на `srm`.
- **Серверная ветка, у которой есть локальный двойник, из списка убирается.**
  Иначе `main` и `origin/main` стояли бы двумя строками, и выбор между ними
  был бы выбором без разницы: обе ведут на ту же локальную ветку.

Дата нужна для сортировки по свежести — «где я работал недавно». Абсолютная
дата не показывается: в списке веток важен порядок, а не точный момент.

### Операции — `Sources/PathwayCore/GitService.swift`

```swift
public func branches(at repository: URL) async throws -> [Branch]
public func switchBranch(to name: String, at repository: URL) async throws
public func switchToRemote(_ name: String, at repository: URL) async throws
```

`switch`, а не `checkout`: у `checkout` две несвязанные роли (сменить ветку и
восстановить файл), и опечатка в аргументе там означает потерю правок.
`switch` умеет только первое.

`switchToRemote` передаёт `--track origin/<имя>`, и это **отдельный метод, а
не флаг**: снаружи это разные действия — «перейти» и «завести у себя», и
кнопка в форме меняет надпись именно по нему.

### Ошибка переключения — `GitError`

Отказ git разбирается в текст с именами файлов. Формат снят опытом:

```
error: Your local changes to the following files would be overwritten by checkout:
	a.txt
	b.txt
Please commit your changes or stash them before you switch branches.
Aborting
```

Имена — строки с табуляцией между заголовком `error:` и строкой `Please
commit`. Разбор берёт их оттуда, а не выводит из своего `git status`:
git знает точно, что мешает.

Текст с действием, а не с диагнозом — правило проекта: «Закоммитьте их или
отложите через git stash, затем повторите».

### Модель — `BrowserModel`

```swift
public private(set) var branches: [Branch] = []
public func loadBranches(at repository: URL? = nil) async
public func switchBranch(to: Branch, at repository: URL? = nil)
```

Необязательная цель — по той же причине, что у остальных git-методов: правый
клик по невыделенной строке действует на неё.

После успешного переключения зовётся `refreshRepositoryInBackground()` и
`reloadAsync()`: сменилась не только ветка, но и содержимое рабочего дерева.

### Подменю — `Sources/Pathway/FileListView.swift`

Пять недавних локальных веток, галочка у текущей, затем «Все ветки…».

- **Пять, не больше.** В `srm` веток 75 — вывались они все, подменю ушло бы
  за край экрана.
- **Только локальные.** Серверная требует создания ветки, и в списке без
  пояснения это выглядело бы обычным переходом.
- **Список читается при открытии подменю**, синхронно: 16 мс на 75 веток, а
  `menuNeedsUpdate` обязан вернуть готовое меню — асинхронно наполнить его
  уже нечем.

### Дерево префиксов — `Sources/PathwayCore/BranchTree.swift`

Ветки группируются по сегментам имени: `feature/SRM/141` становится папкой
`feature` → папкой `SRM` → листом `141`, как в PhpStorm.

Не украшение: в рабочем репозитории 63 ветки из 70 начинаются с
`feature/SRM/`, и плоским списком это стена одинаковых строк, где различается
только хвост. Проверено на живых данных — 65 серверных веток сворачиваются в
два узла верхнего уровня.

Три решения:

- **Цепочка папок с единственным ребёнком схлопывается**: `feature` → `SRM` →
  62 ветки показывается как одна строка `feature/SRM`. Два раскрытия ради
  одного пути — лишняя работа руками.
- **Строка ветки показывает хвост, а не полное имя**: префикс уже назван
  папкой выше, и повторять `feature/SRM/` в каждой из 62 строк незачем.
- **Раскрытые папки запоминаются по полному пути, а не по имени**: хвост
  `SRM` встречается под разными префиксами, и по имени раскрывались бы обе.

При поиске раскрыто всё: свёрнутая папка спрятала бы найденное, и человек
решил бы, что совпадений нет. Фильтр применяется **до** сборки дерева, поэтому
в нём остаются только совпавшие ветки.

Рядом с папкой стоит число веток под ней: свёрнутая `feature/SRM` без него не
говорит, стоит ли её раскрывать — там может быть одна ветка, а может
шестьдесят две.

### Меню чипа — `Sources/Pathway/AddressBarView.swift`

Те же пять недавних веток и «Все ветки…», что и в контекстном меню: стоя
внутри проекта, переключаться приходится оттуда, где показана текущая ветка.

Ветки читаются **заранее**, в `.task(id: currentRepository)`, а не при
открытии меню: SwiftUI строит содержимое `Menu` до показа, и асинхронная
загрузка успела бы только к следующему открытию — первый клик показал бы
пустое место. Ключ задачи — сам `RepositoryState`: его `branch` входит в
`Equatable`, поэтому после переключения список перечитывается сам.

Синхронный `BranchReader` здесь не годится в отличие от `NSMenu`: он
заблокировал бы отрисовку адресной строки, а не только показ меню.

Галочка у текущей ветки — текстом, а не `Toggle`: пункт должен остаться
кнопкой, а `Toggle` в `Menu` рисуется переключателем и обещает состояние,
которого у ветки нет.

### Форма — `Sources/Pathway/BranchSwitchSheet.swift`

Поиск, две группы («Локальные», «На сервере»), дерево внутри каждой,
относительные даты.

- **Поиск обязателен**, не украшение: 75 веток без него не выбрать.
- **Текущая ветка помечена и не выбирается** — кнопка на ней гаснет.
  Переключение на себя git пропустит, но кнопка, которая ничего не делает,
  выглядит сломанной.
- **Кнопка меняет надпись** на «Создать и переключить» для серверной ветки,
  и полоска объясняет, что будет создана привязка к `origin/<имя>`.

Открывается через `AppState.pendingBranchSwitch` — обратный канал «Core
просит UI», как `pendingCompress` и `pendingClone`.

## Поток данных

```
git for-each-ref (16 мс)
    → BranchList.parse
        → GitService.branches
            → BrowserModel.branches
                ├→ подменю: 5 недавних локальных
                └→ форма: все, с поиском и группами
                        ↓
                   git switch [--track]
                        ↓
          успех → refreshRepository + reloadAsync
          отказ → GitError с именами файлов → errorMessage
```

## Тесты

`BranchListTests`:

- разбирает локальные и серверные, отличая по префиксу `origin/`;
- запись с непустым `symref` в список не попадает: это `origin/HEAD`, и в
  выводе она зовётся `origin`, а не `origin/HEAD`;
- серверная с локальным двойником отсеивается, локальная остаётся;
- текущая помечена по имени из `HEAD`, а не по позиции в выводе;
- порядок сохраняется тот, что дал git (`--sort=-committerdate`), а не
  алфавитный;
- пустой вывод даёт пустой список, а не ошибку.

`GitOperationsTests`:

- `switchBranch` зовёт `switch <имя>`, а не `checkout`;
- `switchToRemote` передаёт `--track origin/<имя>`;
- обе идут в каталог из цели.

`GitErrorTests`:

- отказ с двумя файлами даёт текст, где перечислены оба;
- в тексте есть подсказка про commit или stash, а не только жалоба git;
- отказ без списка файлов не теряется — показывается текст git.

`BranchTreeTests`:

- ветка со слэшами становится вложенными папками;
- цепочка из одной папки схлопывается, а папка с двумя ветвями — нет;
- порядок по свежести сохраняется: папка встаёт на место своей первой ветки;
- полный путь узла сохраняется, а не только видимый хвост;
- ветка без слэша остаётся листом верхнего уровня;
- ветка и папка с одним именем: лист важнее, на него можно переключиться.

`BrowserGitTests`:

- `switchBranch` при явной цели идёт в неё, а не в выделенное;
- после успеха список перечитывается (ветка меняет рабочее дерево).

## Ручной чек-лист

1. Правый клик по проекту → подменю → пять веток, галочка у текущей.
1а. Внутри проекта: клик по чипу в адресной строке → те же ветки и «Все ветки…».
2. Выбор ветки из подменю переключает, чип обновляется.
3. Список файлов после переключения показывает содержимое новой ветки.
4. «Все ветки…» открывает форму, локальные и серверные разделены.
4а. Ветки вида `feature/SRM/141` собраны в папки, рядом с папкой — число веток.
4б. Клик по папке раскрывает и сворачивает её; поиск раскрывает всё.
5. Поиск фильтрует обе группы.
6. Текущая ветка помечена, кнопка на ней неактивна.
7. Выбор серверной меняет надпись кнопки и показывает полоску про привязку.
8. Переключение на серверную создаёт локальную с upstream (`git status`
   показывает связь).
9. Незакоммиченные правки, не конфликтующие с целью, переезжают вместе.
10. Конфликтующие правки дают диалог с именами файлов, ветка не меняется.
11. Репозиторий без сервера: группа «На сервере» отсутствует, не пуста.
12. Отделённая голова: подменю открывается, текущей ветки в списке нет.
13. Форма в проекте с 75 ветками открывается без заметной паузы.

## Вне рамок

- **Создание ветки.** Нужны поле имени, выбор точки ветвления и решение про
  push. Отдельная задача: смешать с выбором из списка — сделать обе половины
  хуже.
- **Stash одной кнопкой в диалоге ошибки.** Stash — скрытое хранилище, о
  котором потом надо помнить; спрятать его за кнопкой «просто переключи»
  значит однажды потерять день работы.
- **Удаление и переименование веток.** Разрушительно, требует своих
  подтверждений.
- **Расхождение `↑↓` в списке веток.** `git status` на каждую строку — та же
  цена, по которой отвергнут статус в колонке.
- **Своя проверка «дерево грязное» перед переключением.** git проверяет
  точнее и отказывается сам; наша назвала бы виноватыми все правки.
