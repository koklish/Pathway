# Собственное хранилище паролей к серверам

Дата: 2026-07-27

## Цель

Убрать диалог доступа к Связке ключей, который macOS показывает при переподключении
к сохранённому серверу. Учётные данные переезжают в зашифрованный файл приложения,
Связка ключей перестаёт участвовать в работе — кроме разового переноса того, что в
ней уже лежит.

Диалог возникает в единственном месте: `ServerConnection.connect` читает сохранённый
пароль через `credentials.load`, а чтение защищённых данных записи macOS сопровождает
запросом разрешения. Остальные обращения (`exists`, `savedUser`) читают атрибуты и
диалога не дают — это уже учтено в коде и подтверждается тем, что в других сценариях
пользователи диалога не видят.

Причина диалога — ad-hoc подпись без Developer ID: она меняется от сборки к сборке,
и macOS считает каждую новую версию другой программой. Починить это подписью нельзя
по той же причине, по которой самообновление обходится без Gatekeeper — платного
аккаунта Apple у проекта нет.

### Модель угроз

Ключ шифрования выводится из машины и пользователя, а не из секрета, который знает
человек. Отсюда граница защиты, названная явно:

- файл **не** расшифруется на другой машине и у другого пользователя системы;
- файл **расшифруется** любым процессом, запущенным от имени этого пользователя,
  если он знает алгоритм.

Второе — сознательная плата за отсутствие диалогов. Для паролей к внутренним файловым
шарам в доверенной сети это приемлемо; для менеджера паролей было бы нет. Связка
ключей защищает строго лучше, и именно её защита стоит того диалога, который просили
убрать: одно неотделимо от другого.

## Архитектура

### FileCredentialStore — `Sources/PathwayCore/FileCredentialStore.swift`

Третья реализация существующего протокола `CredentialStoring`. Ни одна строка
`ServerConnection` не меняется: протокол вводился ровно ради такой подмены.

Файл — `~/Library/Application Support/Pathway/credentials.dat`, права `0600`.
Это первая запись проекта в `Application Support`: каталог создаётся при первом
сохранении. `UserDefaults` не годится — система кэширует plist, синхронизирует его и
отдаёт через `defaults read`; пароли там не место даже зашифрованными.

Содержимое — JSON-словарь `[ключ адреса: {user, password}]`, зашифрованный целиком
одним блоком. Поэлементное шифрование ничего не дало бы: файл всё равно читается и
пишется целиком, а один блок скрывает и число сохранённых серверов.

Ключ адреса — тот же, что в `InMemoryCredentialStore`: `scheme://host/share`.
Различать серверы по хосту недостаточно — на одном хосте живут ресурсы с разными
правами.

Шифрование — `CryptoKit`, `AES.GCM`. GCM, а не CBC: он проверяет целостность сам, и
подменённый или повреждённый файл отличим от верного. Без проверки расшифровка мусора
вернула бы мусорную строку вместо честной ошибки.

Ключ выводится `HKDF<SHA256>` из аппаратного UUID платы (`IOPlatformUUID`) и UID
пользователя. Не PBKDF2: паролю пользователя здесь взяться неоткуда, растягивать
нечего, а HKDF предназначен ровно для вывода ключа из уже случайного материала.
Соль — константа в коде; секретом она не является, её задача — разделить контексты.

Замена материнской платы равносильна потере паролей: их придётся ввести заново.

Путь к файлу — параметр `init` со значением по умолчанию, как `UserDefaults` в
`ServerBookmarks`. Иначе тесты писали бы в настоящий `Application Support`.

### MachineIdentity — граница с IOKit

```swift
public protocol MachineIdentifying: Sendable {
    var identifier: String { get }
}
```

Обращение к IOKit прячется за протоколом — тестам нужен предсказуемый ключ, а IOKit
его не даёт: на CI устройства может не быть вовсе, а значение непредсказуемо. Тот же
приём, что `Mounting`, `ReleaseFetching` и `AppTerminating`. Новая граница с системой
вводится так же, как все прежние.

### MigratingCredentialStore — `Sources/PathwayCore/MigratingCredentialStore.swift`

Обёртка над двумя хранилищами: `primary` (файл) и `legacy` (Связка). Отдельный тип, а
не ветвление внутри `FileCredentialStore`: миграция временная и однажды удалится
целиком, а хранилище останется.

| Метод | Поведение |
|---|---|
| `load` | Файл. При промахе — Связка; при успехе записать в файл и **удалить из Связки** |
| `exists` | Файл, при промахе Связка |
| `savedUser` | Файл, при промахе Связка |
| `save` | Только файл |
| `delete` | Оба |

Порядок в `load` обязателен: сначала запись в файл, потом удаление из Связки.
Обратный порядок при сбое записи потерял бы пароль совсем. Удаление диалога не
вызывает, поэтому второй раз тот же сервер не спросит.

`save` в Связку не пишет никогда — новые пароли туда не попадают.

`delete` стирает из обоих: «Забыть пароль», не тронувший Связку, воскресил бы пароль
при следующем подключении.

**Признака «миграция завершена» нет намеренно.** Флаг в `UserDefaults` пришлось бы
согласовывать с реальностью, а она меняется независимо: запись в Связке удаляется
руками, файл теряется. Пустой ответ Связки стоит один запрос без диалога — дешевле
спрашивать каждый раз, чем хранить флаг, который врёт.

**Миграция происходит только при успешном чтении.** Отмена диалога Связки даёт
ошибку `SecItemCopyMatching`, `load` возвращает nil, приложение показывает экран
входа — как при отсутствующем пароле. Диалог повторится при следующей попытке;
запоминать отказ не станем, пользователь мог промахнуться.

Обёртка удаляется через несколько версий заменой одной строки в
`ServerConnection.init` — записано здесь, чтобы через полгода не гадать, зачем слой.

### Сборка — `ServerConnection.swift`

Меняется одно значение по умолчанию:

```swift
credentials: any CredentialStoring = MigratingCredentialStore(
    primary: FileCredentialStore(),
    legacy: KeychainCredentialStore()
)
```

`connect`, `updateSettings`, `forgetPassword`, `ConnectServerModel`, `NetworkSection`
не трогаются.

### Комментарии, требующие правки

- `CredentialStoring.exists` и `savedUser` — доктексты объясняют разделение диалогом
  Связки. В файловой реализации диалога нет, но разделение остаётся осмысленным ради
  `KeychainCredentialStore` на время миграции. Причину переписать, методы оставить.
- `ServerConnection.connect` — комментарий про «именно чтение данных пароля заставляет
  macOS показать диалог» после миграции верен лишь для перенесённых записей.
- `ServerBookmarks` — «пароли живут в Связке ключей» больше не соответствует истине.

## Поток данных

Подключение к серверу с уже перенесённым паролем:

```
connect → MigratingCredentialStore.load → файл расшифрован в памяти → NetFS
```

Ни одного обращения к ОС за разрешением.

Первое переподключение после обновления добавляет один шаг: чтение Связки с диалогом,
запись в файл, удаление из Связки. Дальше — путь выше.

## Интерфейс

Не меняется. «Забыть пароль» и плейсхолдер «сохранён» работают как работали, просто
над другим хранилищем.

Пояснения о месте хранения не добавляем: пользователь просил, чтобы его перестали
спрашивать, — рассказ о внутреннем устройстве вернул бы ту же нагрузку другим
способом. «Забыть пароль» описывает результат точно независимо от места.

## Ошибки

Хранилище учётных данных не показывает алертов. Повреждённый файл, неподошедший ключ,
недоступный каталог — всё это ведёт себя как «пароля нет»: показывается экран входа,
пользователь вводит пароль и едет дальше. Текст «не удалось расшифровать AES-GCM» не
помогает ничем.

- **Чтение** (`load`, `exists`, `savedUser`) ошибок не бросает — сигнатуры протокола
  уже такие. Нечитаемый файл равен пустому хранилищу.
- **Запись** (`save`, `delete`) бросает, как и раньше; в `ServerConnection` она везде
  вызывается через `try?`. Неудача сохранения означает лишь, что в следующий раз
  пароль спросят снова, — рушить состоявшееся подключение алертом неправильно.
- **Повреждённый файл при записи перезаписывается целиком.** Спасать нечитаемое
  содержимое нечем: ключ не подошёл, разобрать его невозможно.

Это отличается от правила «текст ошибки всегда рождается в Core, UI его только
показывает»: здесь ошибка не показывается вовсе. Разница в том, что у файловых
операций отказ окончателен и требует решения человека, а у хранилища паролей есть
корректный запасной путь к тому же результату.

`CredentialError` при миграции тоже глотается. Логирования в проекте нет, заводить
его ради одного случая — отдельная задача.

## Тесты

Новый файл `Tests/PathwayCoreTests/CredentialStoreTests.swift`. Каталог — из
`withTempDirAsync`, настоящий `Application Support` не трогается. `MachineIdentifying`
в тестах — фиксированная строка.

### `@Suite("Файловое хранилище учётных данных")`

1. сохраняет и возвращает логин с паролем;
2. отдаёт nil для незнакомого адреса;
3. `delete` стирает запись, повторный `delete` не ошибка;
4. повторный `save` заменяет прежние логин и пароль, а не добавляет вторую запись;
5. ключом служит полный адрес, **а не только хост** — два ресурса на одном сервере
   хранятся раздельно;
6. переживает пересоздание хранилища — новый экземпляр над тем же файлом читает
   записанное;
7. **файл на диске не содержит пароля в открытом виде** — читаем байты, подстроки
   нет. Тест на то, ради чего всё затевалось;
8. **чужой ключ не расшифровывает файл** — хранилище с другой `MachineIdentifying`
   над тем же файлом отдаёт nil, а не мусор и не падение;
9. права файла — `0600`, а не `0644`.

### `@Suite("Перенос учётных данных из Связки ключей")`

`legacy` — `InMemoryCredentialStore`, его счётчики стерегут отсутствие лишних чтений.

1. при наличии записи в файле **устаревшее хранилище не читается вовсе**
   (`legacy.loadCount == 0`) — главный тест: он стережёт отсутствие диалога;
2. при промахе в файле пароль берётся из устаревшего;
3. после переноса запись появляется в файле **и исчезает из устаревшего**;
4. после переноса повторный `load` не трогает устаревшее;
5. `save` пишет только в файл — `legacy` остаётся пустым;
6. `delete` стирает из обоих.

## Ручной чек-лист

- [ ] Обновиться с предыдущей версии, где пароли лежат в Связке.
- [ ] Подключиться к серверу с сохранённым паролем — диалог Связки появляется **один
      раз**, подключение проходит.
- [ ] Отключиться и подключиться снова — диалога **нет**.
- [ ] Перезапустить приложение, подключиться — диалога нет.
- [ ] Открыть системную «Связку ключей» — записи перенесённого сервера там нет.
- [ ] «Забыть пароль» → подключение спрашивает пароль заново.
- [ ] Сохранить пароль заново с галочкой «Запомнить» → переподключение молчаливое,
      в Связке ключей запись не появилась.
- [ ] Отменить диалог Связки при первом переподключении → показан экран входа, а не
      ошибка.
- [ ] Изменить настройки сервера (смена логина без ввода пароля) → пароль сохранён,
      подключение проходит.
- [ ] Гостевой сервер: подключение без учётных данных работает, файл не создаётся.
- [ ] Испортить `credentials.dat` произвольными байтами → приложение просит пароль,
      не падает и не показывает ошибку расшифровки.

## Вне рамок

- **Мастер-пароль приложения.** Дал бы защиту от процесса, работающего от имени
  пользователя, но вернул бы ровно то, что просили убрать, — вопрос при подключении.
- **Ключ в Связке ключей, данные в файле.** Обращение к Связке стало бы одно вместо
  многих, но диалог остался бы — то есть задача не решена.
- **Стабильная подпись вместо переезда.** Правильное решение по существу, упирается в
  отсутствие платного аккаунта Apple. То же ограничение, что у самообновления.
- **Разовая миграция всех записей при старте.** Дала бы пачку диалогов на запуске, в
  том числе для серверов, которыми не пользуются.
- **Флаг «миграция завершена».** Разошёлся бы с реальностью; см. выше.
- **Пояснение в интерфейсе о месте хранения.** Добавляет текста в плотный диалог ради
  сведения, которое пользователю не нужно.
- **Синхронизация паролей между машинами.** Прямо противоречит выбранной схеме ключа.
- **Логирование ошибок хранилища.** Нужна система логирования, которой в проекте нет.
