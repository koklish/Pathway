# Логин как часть идентичности сервера

## Цель

Разрешить одновременную работу с одним сервером под разными учётными записями и
показать в сайдбаре, под какой из них подключён каждый том.

Сейчас логин не входит в идентичность сервера вовсе: `ServerAddress.parse`
отбрасывает часть `user@` (ServerAddress.swift:91-94), а закладки, пароли, точки
монтирования и индикатор «подключается» ключуются строкой `ServerAddress.key`.
Отсюда наблюдаемое поведение: подключение вторым логином вытесняет первое —
`ServerBookmarks.remember` удаляет запись с тем же адресом
(ServerBookmarks.swift:63), `FileCredentialStore` перезаписывает пароль по тому
же ключу, а `MountedServers.deduplicated` схлопывает `/Volumes/MAIN` и
`/Volumes/MAIN-1` в одну строку, считая второй том следом прошлого подключения.

Понять же, под кем ты подключён, нельзя нигде: логин доступен только чтением
хранилища паролей, а оно на настоящей Связке ключей открывает системный диалог
доступа — цена, которую CLAUDE.md велит платить только по необходимости.

## Архитектура

### `ServerAddress` — новое поле `user`

```swift
public let user: String?
```

Логин входит в `key`, `Hashable` и `displayName`. `parse` перестаёт выбрасывать
`user@host` и сохраняет логин; `url` подставляет его обратно в строку адреса.

Это единственное место, где заводится новая идентичность. Все четыре подсистемы
уже ключуются через `key`, поэтому разделение по логину достаётся им даром — ни
одна не получает нового параметра.

`nil`, а не пустая строка, когда логина нет: пустая строка сделала бы
`smb://@nas/share` валидным ключом, отличным от `smb://nas/share`, и старые
закладки разъехались бы с новыми на пустом месте.

Побочная польза: `f_mntfromname` от системы для SMB имеет вид `//ivan@nas/share`
— логин там уже есть, и сегодня `parse` его теряет. После правки подхват чужих
монтирований (`adoptExistingMounts`) начнёт различать тома по логину сам.

### `ServerBookmark` — гость в идентификаторе

`isGuest` уже есть в структуре, но `id` равен `address`. Гость по решению
владельца — отдельная запись, поэтому `id` становится `address + "|guest"` для
гостевых закладок и остаётся `address` для остальных.

Именно `id`, а не `address`: адрес у гостевой и логиновой записи на один ресурс
совпадает по определению (гость — это отсутствие логина), и без разделения в
идентификаторе они схлопнулись бы обратно. Сравнения в `remember`, `remove`,
`bookmark(for:)`, `setGuest` и `replace` переводятся с `address` на `id`.

### `MountedServers.deduplicated` — схлопывать только одинаковые логины

Метод сохраняется вместе со своим смыслом: повторное монтирование одного и того
же ресурса тем же пользователем — по-прежнему одна строка. Различаются теперь
только логины, и различает их сам `ServerAddress`, ставший `Hashable` с учётом
`user`. Тело метода не меняется — меняется поведение его ключа.

### `NetworkSection` — две строки вместо одной

Снимается `seen.insert(server.key)` (NetworkSection.swift:36), гасящий вторую
запись на тот же адрес: теперь ключи разных логинов различны, и схлопывать
нечего. Строка сервера получает подпись логина.

### `VolumesSection` — подпись у сетевых дисков

`VolumeUsage` знает только точку монтирования и имя тома; логина в нём нет и не
будет — читается он из `getmntinfo` отдельным путём. Подпись берётся
сопоставлением по точке монтирования с `MountedServers.networkVolumes`, где
после правки `parse` логин уже есть.

Сопоставление по `mountPoint`, а не по имени: имена томов совпадают у одного
ресурса, подключённого дважды («MAIN» и «MAIN»), а точки монтирования уникальны
по определению — их выдаёт система.

Локальные диски подписи не получают: у них нет ни сервера, ни логина.

## Поток данных

```
ввод «smb://ivan@nas/share»
   → ServerAddress(scheme: smb, host: nas, share: share, user: ivan)
   → key = "smb://ivan@nas/share"
        ├─ ServerBookmarks     — своя запись, не вытесняет petr@nas
        ├─ FileCredentialStore — свой пароль
        ├─ MountedServers      — своя точка монтирования
        └─ NetworkSection      — своя строка с подписью «ivan»
```

## Вид

Строка сервера в «СЕТИ» и строка сетевого диска в «ДИСКАХ» получают вторую
строку — логин, 10 pt, вторичным цветом, с отбивкой на ширину иконки. Ровно те
же величины, что у подписи занятости в `VolumeRow` (SidebarView.swift:527-530):
приём в сайдбаре уже есть, второй его вариант выглядел бы небрежностью.

- логин известен → «ivan»;
- гостевая закладка → «гость»;
- логина нет (старая закладка, подключение без учётных данных) → подписи нет
  вовсе, строка выглядит ровно как сегодня.

Пустая строка вместо подписи не рисуется: она съела бы высоту и разъехалась с
соседними строками без логина.

## Совместимость

Миграции нет — по решению владельца старые данные подхватываются как есть.

Закладка `smb://nas.local/Общие`, сохранённая до правки, парсится в адрес с
`user == nil`, работает по-прежнему и показывается без подписи. Её пароль лежит
в хранилище под тем же ключом и остаётся доступен. Логин появится у неё при
следующем подключении с вводом учётных данных — как у новой записи.

Отвергнута разовая миграция «прочитать логин из хранилища паролей и вписать в
закладки»: она требует чтения Связки ключей на старте приложения, то есть того
самого системного диалога доступа, ради избегания которого в `CredentialStoring`
заведён отдельный `exists` (см. CLAUDE.md, «Сетевые серверы»).

## Тесты

Все в `PathwayCore`: `ServerAddressTests`, `CredentialStoreTests`,
`MountedServersTests`. Закладки тестируются в `ServerConnectionTests` —
отдельного файла у `ServerBookmarks` нет.

**Разбор адреса:**
- `parse` сохраняет логин из `smb://ivan@nas/share`;
- `parse` без логина даёт `user == nil`, а не пустую строку;
- логин уцелел при разборе `f_mntfromname` вида `//ivan@nas/share`;
- `url` возвращает логин обратно в строку адреса;
- UNC-запись `\\ivan@nas\share` тоже отдаёт логин.

**Ключ:**
- ключом служит полный адрес с логином, а не только хост и шара;
- `ivan@nas` и `petr@nas` дают разные ключи;
- одинаковые логины дают совпадающие ключи;
- адрес без логина сохраняет прежний ключ — старые закладки не осиротели.

**Закладки:**
- две записи на один адрес с разными логинами сосуществуют;
- `remember` вторым логином не вытесняет первый;
- `remove` убирает только свою запись;
- гостевая и логиновая записи на один адрес — разные записи;
- `setGuest` не задевает соседнюю запись с тем же адресом.

**Пароли:**
- пароли двух логинов на один адрес не пересекаются;
- удаление пароля одного логина оставляет пароль второго;
- `exists` для несохранённого логина не читает пароль сохранённого
  (проверяется счётчиками `InMemoryCredentialStore`).

**Монтирование:**
- `deduplicated` схлопывает повторы одного логина;
- `deduplicated` сохраняет оба тома при разных логинах;
- `mountPoint(for:)` отдаёт свою точку каждому логину.

## Ручной чек-лист

1. Подключиться к FTP под первым логином, затем под вторым — в «СЕТИ» две
   строки, обе с зелёной точкой.
2. В «ДИСКАХ» два тома, каждый подписан своим логином.
3. Пароли не перепутаны: отключить и подключить заново каждый — не спрашивает.
4. Старая закладка (до обновления) работает и показывается без подписи.
5. Удаление одной записи не трогает вторую, включая её пароль.
6. Гостевое подключение к тому же адресу — третья строка с подписью «гость».
7. Тёмная тема, узкий сайдбар: подпись усекается, вёрстка цела.

## Вне рамок

- **Миграция старых закладок** — причина выше.
- **Смена логина у существующей закладки.** Отдельный логин — отдельная запись;
  «переименование» учётной записи означало бы перенос пароля между ключами
  хранилища, а это операция с необратимой половиной (удалением) ради удобства,
  которое достигается созданием второй закладки.
- **Показ логина в адресной строке и заголовке окна.** Владелец уточнил, что
  речь о сайдбаре; адресная строка показывает путь, а не учётную запись.
- **`ProtocolProbe` и диалог подключения.** Получают адрес целиком и о новом
  поле знать не обязаны.
