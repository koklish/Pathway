# Git в списке файлов

## Цель

Видеть состояние git прямо в файловом менеджере и выполнять общие операции над
репозиторием, не уходя в терминал.

Сценарий, ради которого всё затевается: в `~/PhpstormProjects` лежат все проекты,
сама папка репозиторием не является, а каждая папка внутри — является, и у каждой
своя ветка. Нужно видеть эти ветки списком, в строках, а зайдя внутрь проекта —
не терять из виду, на какой ветке находишься.

Отсюда две разные вещи, отвечающие на два разных вопроса:

- **Колонка «Ветка»** — «какая ветка у каждой из этих папок». Работает, когда
  стоишь над проектами.
- **Индикатор в панели сверху** — «где сейчас я». Работает, когда находишься
  внутри проекта, на любой глубине.

Правило одно и то же везде, режимов и переключений нет: *строка получает ветку,
если сама является репозиторием*; *окно показывает ветку, если текущий путь
находится внутри репозитория*.

Плюс четыре операции над репозиторием целиком: Clone, Fetch, Pull, Push.

## Архитектура

### Способ работы с git: вызов процесса

`/usr/bin/git` запускается как внешний процесс, вывод разбирается. Не libgit2.

Причина решающая: `git push` по SSH-ключу с passphrase в Связке ключей просто
работает — git сам возьмёт `~/.gitconfig`, credential helper и `ssh-agent`
пользователя. С libgit2 аутентификацию пришлось бы решать самому, а это
основная сложность всей задачи. Плюс C-зависимость в проекте, у которого
зависимостей нет вовсе.

Цена названа явно: `git status` на большом репозитории стоит сотни миллисекунд,
и это прячется за асинхронностью (см. «Поток данных»).

### GitRunning — граница с ОС

`Sources/PathwayCore/GitRunning.swift`

Протокол с единственным методом: запустить `git` с аргументами в рабочей
директории, вернуть stdout, stderr и код возврата. Реализация `GitCLI`
запускает `/usr/bin/git`; в тестах — фейк с заготовленным выводом.

Тот же приём, что `Mounting`, `CredentialStoring`, `TerminalRunning`,
`ReleaseFetching` — ко всем границам с системой в проекте применён один подход,
и новая граница вводится так же.

Окружение процесса задаётся жёстко:

```
GIT_TERMINAL_PROMPT=0
GIT_ASKPASS=/usr/bin/false
SSH_ASKPASS=/usr/bin/false
```

Это решение по авторизации. Без него процесс, запущенный из приложения,
**зависнет навсегда**, ожидая ввод пароля в терминал, которого нет: у приложения
нет tty, и git будет ждать вечно. С этими переменными git при необходимости
ввода сразу падает с узнаваемой ошибкой, которую мы превращаем в понятный текст.

Собственный диалог ввода пароля через `GIT_ASKPASS`-мост отвергнут — см. «Вне рамок».

### GitRepository — является ли папка репозиторием и на какой ветке

`Sources/PathwayCore/GitRepository.swift`

Ветка читается **не запуском git, а чтением `.git/HEAD`.** Это обычный текстовый
файл с одной строкой `ref: refs/heads/main`. Одно чтение мелкого файла против
запуска процесса ценой порядка 10 мс — а колонка требует этого для каждой строки
списка, то есть сотню раз при заходе в папку с проектами. Через процессы
колонка стоила бы секунду, через чтение файла — единицы миллисекунд.

Разбираемые формы:

- `ref: refs/heads/<имя>` — обычная ветка, показываем имя
- голый SHA — detached HEAD, показываем короткий хеш
- `.git` является **файлом** со строкой `gitdir: <путь>` — worktree или submodule,
  идём по указанному пути. Без этого проекты с подмодулями и worktree выглядели
  бы как обычные папки
- нечитаемое или неожиданное содержимое → nil, без ошибки: битый `.git` не повод
  ронять загрузку каталога

Поиск корня репозитория вверх по пути — отдельный метод для индикатора
текущей папки. Подъём **обязан останавливаться на границе тома**, а не идти
до `/`: на сетевом диске каждый шаг вверх — обращение к SMB, и промах стоил бы
заметной паузы при каждой смене папки.

### GitStatus — впереди/позади и грязное дерево

`Sources/PathwayCore/GitStatus.swift`

Один вызов `git status --porcelain=v2 --branch -z` даёт всё сразу: ветку,
счётчики относительно upstream, наличие незакоммиченных правок.

Разбор вывода — чистая функция `GitStatus.parse(_ output: String) -> GitStatus`,
без диска и без репозитория, тестируется на строковых образцах.

Отсутствие upstream — **не то же самое, что «0 впереди, 0 позади»**: у ветки без
upstream счётчиков нет вовсе, и показывать `↑0 ↓0` было бы враньём. Счётчики
опциональны.

### Колонка «Ветка»

Ветка — новое поле `FileItem.branch: String?`, рядом с `size` и
`modificationDate`. Не отдельный словарь «путь → ветка» на стороне модели:
иначе сортировка по колонке заглядывала бы в два источника, а `DirectoryCache`
пришлось бы учить хранить второй набор данных параллельно основному. Кэш хранит
готовые `FileItem`, поэтому ветка попадает в него даром.

В UI — новый случай `Column.branch` в `FileListView`, пятый после `name`,
`modified`, `size`, `kind`. Колонки строятся из `Column.allCases`, механизма
скрытия в проекте нет — «Ветка» есть всегда, как «Размер». Сортировка по
заголовку достаётся из существующего `sortDescriptorPrototype`; в
`SortSettings` добавляется ключ `"branch"`.

Пустые значения уходят **вниз при любом направлении** — иначе сортировка по
ветке показывала бы полэкрана пустых строк, а смысл сортировки в том, чтобы
сгруппировать проекты по веткам.

Колонка не пропадает внутри проекта: вложенные репозитории (подмодули, отдельные
проекты) покажут свою ветку, обычные папки — пусто.

### Индикатор текущей папки

`BrowserModel.currentRepository: GitRepositoryInfo?` — имя ветки, корень
репозитория, счётчики. Обновляется при смене папки.

В UI — рядом с адресной строкой в `AddressBarView`: значок ветки, имя, счётчик
`↑2 ↓1`, когда он ненулевой. Вне репозитория элемента нет.

Место под индикатор имеет фиксированную минимальную ширину и вне репозиториев
просто пустует: элемент, появляющийся и исчезающий, дёргал бы раскладку
адресной строки при каждом переходе из проекта в обычную папку.

Путь и ветка стоят рядом намеренно — это одна мысль, «где я нахожусь».
Разнесённые по разным краям окна, они заставляли бы глаз метаться. Строка
состояния для этого не используется, хотя она в проекте есть.

### Операции: реестр команд

`gitClone`, `gitFetch`, `gitPull`, `gitPush` в `Sources/PathwayCore/Commands.swift`.

Из реестра они автоматически получают заголовок, иконку, доступность и попадают
и в главное меню (`AppCommands.swift`), и в контекстное
(`FileListView.menuNeedsUpdate`) — в этом и смысл реестра, править оба места
поштучно не нужно.

Доступность: Fetch/Pull/Push активны, когда текущая папка внутри репозитория
либо выделена папка-репозиторий. Clone активен всегда — он действует не на
выделенное, а на текущую папку как место назначения, поэтому живёт только в
главном меню.

Шорткаты не назначаются: свободных сочетаний под четыре команды нет, а
конфликтовать со стандартными ради редко нажимаемых сетевых операций незачем.

### Clone: обратный канал «Core просит UI»

Clone требует диалога (URL репозитория, имя папки), а Core не умеет показывать
диалоги. Значит — тот же приём, что `pendingRename`, `pendingCompress`,
`pendingEditPath`: команда выставляет `AppState.pendingClone`, лист его
исполняет и сбрасывает.

Лист поднимает `AppState.isEditingText` и сбрасывает его на `.onDisappear`, а не
на кнопках: Esc закрывает лист мимо них.

## Поток данных

### Ветка в колонке — вторая ступень загрузки

`BrowserModel.reloadAsync` уже устроен как кэш → имена → метаданные. Ветка
читается **в третьей ступени**, вместе с метаданными, на `.utility`.

Первый проход (`DirectoryLoader.loadNames` через `opendir/readdir`) не трогает
диск принципиально — это и есть 0.7 мс против 4824 мс на 510 подпапках. Чтение
`.git/HEAD` — обращение к диску, значит его место строго во втором проходе.

Порядок проверки дешёвый: только для папок → есть ли внутри `.git` → если да,
прочитать одну строку. Для папки без `.git` цена — один `stat`, который
`loadMetadata` и так делает.

Кэширование — даром: только третья ступень пишет в `DirectoryCache`, и она пишет
готовые `FileItem`, в которых ветка уже есть.

### Индикатор — отдельная задача от загрузки каталога

`git status` стоит сотни миллисекунд, поэтому индикатор обновляется **своей
задачей**, не привязанной к загрузке списка: привязка задержала бы отрисовку
файлов ради индикатора.

Защиты от гонок те же две, что и в загрузке каталога, и они не дублируют друг
друга: отмена предыдущей задачи при смене папки и проверка `pane.path` после
каждого `await`. Отмена кооперативна, уже запущенный процесс её не видит.

### Операции — прогресс и отмена

Все четыре ходят в сеть и могут идти минутами. Показываются в существующих
`BrowserModel.operationProgress` / `operationTitle` — там уже есть индикатор в
строке состояния и кнопка отмены, отдельный механизм не нужен.

Отмена — `terminate()` процесса. `try Task.checkCancellation()` ставится
**перед** проверкой кода возврата: убитый по SIGTERM git вернёт ненулевой код и
превратился бы в ложную ошибку вместо `CancellationError`. Ровно та же ловушка,
что уже разобрана в `ArchiveService.run`.

`CancellationError` глотается молча — отмена не ошибка.

После успеха: инвалидация `DirectoryCache` затронутой папки и перезагрузка
списка. Clone создаёт папку, pull меняет файлы — без инвалидации список показывал
бы прошлое состояние.

### Когда ветка обновляется

Наблюдатель FSEvents следит за показанной папкой нерекурсивно, а `.git/HEAD`
проекта лежит уровнем глубже — переключение ветки в терминале событием не
приходит. Рекурсивное слежение за папкой проектов ловило бы каждую запись во
всех проектах: одна сборка или `npm install` дали бы шквал событий ради
строки в колонке.

Поэтому ветка перечитывается там же, где и остальные метаданные: при возврате
в приложение (`refreshAfterReturn`), по ⌘R и при заходе в папку. Переключил
ветку в терминале, вернулся в Проводник — колонка уже новая, и это покрывает
живой сценарий целиком.

Остаётся один случай: оба окна видны одновременно и фокус не переключался.
Тогда колонка показывает прежнюю ветку до ⌘R. Признано допустимым — цена
альтернативы несоразмерна.

### Ошибки

Через `BrowserModel.errorMessage`, текст рождается в Core — UI его только
показывает, как везде в проекте.

Провал авторизации перехватывается отдельно и переводится **с действием** в
тексте, по принятому в проекте образцу: не «ошибка аутентификации», а
«Требуется авторизация. Выполните `git push` в терминале один раз, чтобы система
запомнила учётные данные».

## Тесты

Только `PathwayCore`, swift-testing. UI-тестов в проекте нет принципиально —
вместо них ручной чек-лист ниже.

### GitRepositoryTests

- читает имя ветки из `.git/HEAD`
- при detached HEAD отдаёт короткий хеш, а не полный SHA
- понимает `.git` как файл с `gitdir:` — worktree и submodule
- битый `.git/HEAD` даёт nil, а не ошибку
- папка без `.git` не является репозиторием
- поиск корня вверх находит репозиторий из вложенной папки
- поиск вверх останавливается на границе тома, а не идёт до корня

### GitStatusTests

- разбирает счётчики впереди и позади из `--branch`
- ветка без upstream даёт отсутствие счётчиков, а не нули
- отличает чистое дерево от грязного
- разбирает detached HEAD
- пустой вывод не роняет разбор

### GitOperationsTests

На фейке `GitRunning`:

- fetch, pull, push и clone передают ожидаемые аргументы
- окружение содержит `GIT_TERMINAL_PROMPT=0` и заглушки askpass
- провал авторизации превращается в текст с действием, а не в сырой stderr
- ненулевой код возврата даёт ошибку
- отмена даёт `CancellationError`, а не ошибку от ненулевого кода
- успех инвалидирует кэш затронутой папки

### BranchColumnTests

- ветка попадает в `FileItem` во втором проходе
- первый проход ветку не читает
- папка без `.git` даёт `branch == nil`
- файлы ветку не получают никогда
- сортировка по ветке кладёт пустые вниз при возрастании
- сортировка по ветке кладёт пустые вниз и при убывании

Осторожно с URL: `DirectoryLoader` канонизирует пути (`/var` → `/private/var`),
склеенный вручную путь — нет. Сравнения строить от `model.items[…].url`.

## Ручной чек-лист

1. Открыть `~/PhpstormProjects` — у каждого проекта в колонке «Ветка» видно его
   ветку, у обычных папок пусто
2. Кликнуть заголовок «Ветка» — проекты группируются по веткам, пустые внизу;
   кликнуть ещё раз — порядок обратный, пустые по-прежнему внизу
3. Зайти в проект — индикатор рядом с адресной строкой показывает ветку
4. Провалиться в `Sources/PathwayCore` — индикатор всё ещё показывает ветку
   проекта
5. Выйти в папку без репозитория — индикатор исчез, адресная строка не дёрнулась
6. Переключить ветку в терминале, вернуться — ветка обновилась
7. Проект с detached HEAD показывает короткий хеш
8. Проект с подмодулем: подмодуль показывает свою ветку
9. Меню «Репозиторий» → Fetch на проекте — прогресс в строке состояния,
   счётчик `↓` обновился
10. Pull — файлы в списке обновились без ручного обновления
11. Push при несохранённых учётных данных — понятная ошибка, приложение не зависло
12. Clone — диалог подставил имя папки из адреса; правка имени руками не
    затирается при дальнейшей правке адреса; занятое имя подсвечено красным
13. Clone прошёл — прогресс, новая папка появилась в списке
14. Отмена clone в середине — операция прервалась, ошибки нет
15. Папка с сотней проектов открывается без заметной задержки
16. Репозиторий на SMB не подвешивает список файлов

## Вне рамок

- **Значки статуса файлов, commit, discard, stage, ignore** — пофайловые
  операции. Отдельная граница: они требуют `git status` на каждый показ папки,
  то есть сотни миллисекунд там, где колонка ветки стоит единицы. Заводятся
  отдельными задачами.
- **История, diff, merge, rebase, stash, разрешение конфликтов** — не работа
  файлового менеджера, для них есть готовые инструменты. Реализация была бы
  размером с сам Pathway.
- **Переключение и создание веток** — меняет рабочее дерево и требует решать,
  что делать с незакоммиченными правками. Отдельная задача.
- **Собственный диалог ввода пароля через `GIT_ASKPASS`-мост** — по образцу
  `passwordRequest` для архивов сделать можно, но это большая часть бюджета
  задачи ради редкого пути: на macOS у разработчика обычно уже настроен
  ssh-agent или osxkeychain helper, и push работает молча. Заменён понятной
  ошибкой; вернуться, если упрёмся на практике.
- **libgit2 / SwiftGit2** — тянет C-зависимость в проект без зависимостей и
  заставляет самому решать аутентификацию, которую `git` берёт из системных
  настроек пользователя.
- **Обёртка над внешним git-клиентом** (Fork, GitKraken) — это ярлык, а не
  git в файловом менеджере.
- **Шорткаты для git-команд** — свободных сочетаний нет, конфликтовать со
  стандартными ради редких сетевых операций незачем.
