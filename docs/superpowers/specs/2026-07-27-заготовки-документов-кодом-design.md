# Заготовки документов генерируются кодом

## Цель

Убрать краш приложения при «Создать → документ» и устранить его причину, а не проявление.

Коллеги сообщили: правый клик → «Создать» → «Текстовый документ» роняет приложение,
после чего оно «пропадает с устройства». Отчёт (`/Users/kogan/Downloads/отчет ошибки.rtf`)
указывает причину буквально:

```
Exception Type: EXC_BREAKPOINT (SIGTRAP)
0  libswiftCore.dylib  _assertionFailure(_:_:file:line:flags:)
1  Pathway             closure #1 in variable initialization expression of static NSBundle.module
2  Pathway             one-time initialization function for module
5  Pathway             closure #1 in BrowserModel.createDocument(_:)
```

`Bundle.module` — сгенерированный SPM аксессор. Не найдя ресурсный бандл
`Pathway_PathwayCore.bundle`, он вызывает `fatalError` — то есть **обрушивает процесс**,
а не возвращает ошибку. Наш `DocumentTemplates.templatesRoot` добавляет второй такой
же барьер (`preconditionFailure`), но до него исполнение не доходит: падает раньше.

«Приложение пропадает с устройства» — следствие того же краша: скрипт самообновления
переименовывает старый бандл в `.old` и возвращает его, только если новая версия
не поднялась за минуту; краш в этом окне оставляет систему без `.app`. Плюс
LaunchServices прячет из Launchpad приложение, падающее при каждом запуске.

**Почему предыдущая правка (`8f349d9`) не помогла.** Она добавила копирование
`*.bundle` в `build-app.sh` и `release.sh` и проверку `Tools/check-bundle.sh`. Это
верные шаги, но они защищают только *будущие* сборки. В присланном отчёте
`Version: ???`, `app_version: ""` — упавшая копия собрана не через `release.sh`
(он проставляет версию в `Info.plist` до сборки), то есть у коллеги стоит копия,
собранная до правки.

Главное же в том, что защита скриптами по своей природе — договорённость, а не
гарантия: любой новый способ собрать бандл (ручная сборка, чужой скрипт, Xcode)
воспроизводит ту же ошибку, и узнаётся она крашем у пользователя, а не сборкой.
Пока создание документа зависит от внешнего файла, класс ошибки остаётся живым.

**Решение:** документ генерируется кодом внутри бинарника. Внешнего ресурса нет,
значит нет и того, чему не доехать: краш становится невозможен по устройству
программы, а не по аккуратности сборки.

## Архитектура

### `Sources/PathwayCore/DocumentTemplates.swift`

Убирается `templatesRoot` — единственное место, где жил `Bundle.module`.
Вместе с ним из `all` уходят три пункта iWork (`pages`, `numbers`, `key`).

Форматы iWork закрыты: сгенерировать валидный `.pages` кодом нельзя, а заготовки
можно только хранить файлом — то есть ровно тем внешним ресурсом, от которого
мы избавляемся. Оставить их «как есть» значило бы сохранить в приложении путь,
способный отказать по той же причине; лучше пять пунктов, работающих всегда,
чем восемь, из которых три держатся на удачной сборке.

`DocumentTemplate` получает поле `content: DocumentContent` вместо связи «id ↔
имя файла заготовки».

```swift
public enum DocumentContent: Sendable, Equatable {
    case empty            // txt
    case text(String)     // rtf — готовая строка
    case ooxml(OOXMLKind) // docx, xlsx, pptx — ZIP собирается кодом
}
```

### `Sources/PathwayCore/OOXMLBuilder.swift` (новый)

Собирает минимальный валидный OOXML-документ: ZIP из трёх-четырёх XML-частей.

Замер, обосновывающий необходимость: `.docx` — ZIP-контейнер, и пустой файл
нулевой длины им не является:

```
$ unzip -l пустой.docx
  End-of-central-directory signature not found.
```

Word такой файл считает повреждённым, и узнаёт об этом пользователь при открытии,
а не при создании. Поэтому «просто пустой файл с нужным расширением» годится
только для `txt` (и, с оговоркой, `rtf`), но не для контейнерных форматов.

ZIP пишется вручную, без сторонних зависимостей: нужен лишь формат store
(без сжатия) — локальный заголовок, данные, центральный каталог, EOCD. Части
маленькие (сотни байт), сжатие не даёт ничего, а `Compression` из системы
потребовала бы возиться с raw-deflate и CRC поверх него.

CRC32 считается своей таблицей — в Foundation его нет.

### `Sources/PathwayCore/FileOperations.swift`

`createDocument(_:in:templatesRoot:)` теряет параметр `templatesRoot` и вместо
копирования пишет сгенерированные данные:

```swift
public func createDocument(_ template: DocumentTemplate, in directory: URL) throws -> URL
```

Ошибка `FileOperationError.templateMissing` удаляется: отсутствовать больше нечему.

### `Sources/PathwayCore/BrowserModel.swift`

Вызов теряет аргумент `templatesRoot: DocumentTemplates.templatesRoot` — то самое
обращение, что стояло в стеке краша.

### Сборочные скрипты и `Package.swift`

`resources: [.copy("Resources/Templates")]` убирается из `Package.swift`, каталог
`Sources/PathwayCore/Resources/Templates` удаляется (685 КБ, из них 460 КБ — `key`).

Копирование `*.bundle` в `build-app.sh` и `release.sh` **остаётся**: таргет без
ресурсов бандла не порождает, цикл просто не находит файлов, а будущий ресурс
в любом таргете окажется на месте без новой правки. Проверка заготовок из
`Tools/check-bundle.sh` уходит — проверять больше нечего.

## Поток данных

```
Контекстное меню → DocumentTemplates.all  (5 пунктов, чистые данные)
        ↓
BrowserModel.createDocument(template)
        ↓
FileOperations.createDocument(template, in: pane.path)
        ↓
template.content
   ├─ .empty      → Data()
   ├─ .text(s)    → Data(s.utf8)
   └─ .ooxml(k)   → OOXMLBuilder.data(for: k)   ← ZIP собирается в памяти
        ↓
запись по уникальному имени → URL → инлайн-редактор имени
```

Ни одного обращения к файловой системе за исходником и ни одного к `Bundle`.

- каждый собранный контейнер распаковывается системным `unzip` без ошибок —
  проверка настоящим распаковщиком, а не только по сигнатуре: именно на этом
  «пустой файл с расширением» и ломается

- в xlsx есть `xl/workbook.xml`, в pptx — `ppt/presentation.xml`

- имена частей и данные не перепутаны местами: содержимое, извлечённое по имени,
  начинается с `<?xml`

## Ручной чек-лист

1. Правый клик в списке → «Создать» → «Текстовый документ» — файл появляется,
   приложение не падает, включается инлайн-редактор имени.
2. То же для RTF, Word, Excel, PowerPoint.
3. Созданный `.docx` открывается в Word без «файл повреждён».
4. Созданный `.xlsx` открывается в Excel, `.pptx` — в PowerPoint.
5. Созданный `.rtf` открывается в TextEdit.
6. Пункты Pages, Numbers, Keynote в меню отсутствуют.
7. Два документа подряд в одной папке → «Новый документ» и «Новый документ 2».
8. Собрать бандл вручную **без** копирования `*.bundle` и убедиться, что
   создание документа всё равно работает — прямая проверка того, что причина
   краша устранена, а не замаскирована.

## Вне рамок

- **Пустой файл с нужным расширением для всех форматов.** Отвергнуто замером:
  `unzip` не читает пустой `.docx`, Word покажет «файл повреждён». Краш ушёл бы,
  но шесть пунктов меню создавали бы неоткрываемые документы — обмен одной
  жалобы на другую. Для `txt` пустой файл сохранён: там он корректен.
- **Оставить iWork, заменив краш обычной ошибкой.** Работало бы, но сохранило бы
  в приложении путь, отказывающий по причине «ресурс не доехал», — тот самый
  класс, ради которого всё и затевается.
- **Сторонняя библиотека ZIP.** Ради четырёх файлов по сотне байт — зависимость
  в таргете, который сегодня не имеет ни одной.
- **Генерация iWork через AppleScript.** Запускала бы Pages ради пустого файла:
  секунды ожидания и запрос разрешения на автоматизацию вместо мгновенного файла.
- **Починка уже разошедшихся копий.** Автообновление заменит бандл штатно.
  Коллеге, у которого приложение не запускается совсем, обновление не придёт
  (проверка идёт изнутри приложения) — такому нужно скачать сборку с GitHub руками.
