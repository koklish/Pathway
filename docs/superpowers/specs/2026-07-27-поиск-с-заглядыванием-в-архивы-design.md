# Поиск с заглядыванием в архивы

## Цель

Поиска в Pathway нет вовсе. Нужен такой, который находит файл и тогда, когда
тот лежит **внутри архива** — включая RAR. Это главная ценность: Spotlight,
Finder и файловые менеджеры внутрь архивов не смотрят.

Проверено прямо: содержимое тестового zip Spotlight не находит, а на сетевых
томах (FTP) индексация вообще отключена (`mdutil -s` → «Indexing disabled»).
То есть системный поиск не закрывает ни один из двух главных сценариев.

Требования, заданные владельцем проекта:

- работает **очень быстро**;
- ищет по именам записей внутри архивов, RAR обязателен;
- область — текущая папка и вложенные;
- главный сценарий — **сотни-тысячи архивов на сетевом диске** (SMB/FTP);
- сопоставление — **нечёткое с ранжированием**, как в VS Code;
- запуск по Enter;
- результаты — плоский список, двойной клик извлекает файл и открывает.

## Замеры, продиктовавшие архитектуру

Всё измерено на этой машине до проектирования; числа — обоснование решений.

| операция | время |
|---|---|
| Spotlight по диску | 100–300 мс |
| листинг архива на 5000 записей (`bsdtar`) | 20 мс |
| **запуск процесса `bsdtar`** | **2,5 мс** |
| 200 архивов последовательно | 455 мс |
| 200 архивов в 8 потоков | 67 мс (6,8×) |
| **чтение хвоста ZIP своим кодом** | **0,03 мс** |
| обход сетевого тома (FTP) | ~9 мс на запись |

Два факта определили всё остальное.

**`bsdtar` читает ZIP насквозь целиком.** Ради списка имён из 95-мегабайтного
архива он прочитал все 95,4 МБ — измерено подачей архива через канал со
счётчиком байт. Он ползёт по локальным заголовкам через данные каждого файла.

**Центральный каталог ZIP лежит в хвосте и стоит килобайты.** Доказано
обратным экспериментом: первые 50 МБ архива забиты нулями, а все 200 записей
всё равно перечислились. По сети это разница между мегабайтами и килобайтами
на каждый архив.

## Архитектура

### Диспетчеризация по формату

Единый инструмент на все форматы был бы либо медленным, либо неполным.

| формат | чем читаем | цена | почему |
|---|---|---|---|
| ZIP (и `.docx`/`.xlsx` — тоже ZIP) | свой парсер центрального каталога | 0,03 мс | оглавление в хвосте, процесс не запускается |
| RAR4, RAR5, 7z, tar.* | `bsdtar -tf` | 2,5 мс + весь файл | оглавление размазано по файлу, дешёвого пути нет |

RAR читается системным `bsdtar` (libarchive 3.7.4) — проверено на настоящих
RAR4 и RAR5. **Сторонние утилиты не нужны и недоступны:** `unar`, `7z`,
`unrar` в системе отсутствуют, а требовать их установки от коллег нельзя.

Отвергнут `unzip -Z1` как основной путь для ZIP: он **портит кириллицу**,
подменяя байты на `?` (`d13f` вместо `d184` для буквы «ф»). Лечится флагом
`-UU`, но процесс всё равно стоит 2,5 мс против 0,03 мс у своего парсера — на
1000 архивов это 2,5 с против 0,03 с.

### Свой парсер ZIP

`Sources/PathwayCore/ZipCentralDirectory.swift`

Читает хвост файла (64 КБ), находит сигнатуру `PK\x05\x06` (End of Central
Directory), от неё — смещение центрального каталога, проходит записи и берёт
имена. Формат стабилен с 1989 года; при неудаче разбора — пустой список, а не
крэш.

Имена берутся как UTF-8, если в записи выставлен бит 11 общих флагов, иначе
CP437 — так велит спецификация ZIP. Без этого русские имена из архивов,
созданных старыми Windows-архиваторами, превратились бы в мусор.

Zip64 (архивы свыше 4 ГБ или 65 535 записей) распознаётся по маркерам
`PK\x06\x06`/`PK\x06\x07`. Такой архив по сети всё равно за порогом размера, но
разбор не должен молча отдавать обрезанный список.

### Конвейер поиска

`Sources/PathwayCore/SearchEngine.swift`

Четыре ступени, каждая отдаёт результаты сразу, не дожидаясь следующей:

1. **Обход каталога** — `opendir`/`readdir` с типом из `d_type`, как в
   `DirectoryLoader`: не трогать диск ни разу, иначе на сетевом томе это
   запрос к серверу на объект.
2. **Сопоставление** — `FuzzyMatcher`, результаты идут в UI потоком.
3. **Отбор архивов** — прошедшие порог размера.
4. **Вскрытие архивов** — параллельно, 6–8 задач.

Обычные файлы находятся за миллисекунды и показываются, **пока архивы ещё
вскрываются**: ждать самый медленный архив ради первого результата не нужно.

Параллелизм ограничен 6–8 задачами: замер дал 6,8× ускорения, а на сетевом
томе больший параллелизм забивает канал, не ускоряя.

Отмена — по образцу `BrowserModel.reloadAsync`: `task.cancel()` при новом
запросе **и** проверка актуальности после каждого `await`. Две защиты не
дублируют друг друга: отмена кооперативна, запущенный `Task.detached` её не
видит.

### Ранжирование

`Sources/PathwayCore/FuzzyMatcher.swift` — чистая функция, без ввода-вывода.

Возвращает балл, а не «да/нет»; список сортируется по нему. Иначе нечёткий
поиск даёт мусор: короткий запрос совпадёт почти со всем.

| случай | пример (запрос «дог») | балл |
|---|---|---|
| точное совпадение имени | `дог.txt` | 1000 |
| начало имени | `**Дог**овор.pdf` | 900 |
| начало слова внутри | `Акт-**дог**овор.pdf` | 800 |
| подстрока где угодно | `перезаклю**дог**овор` | 700 |
| нечёткое, буквы по порядку | `**Д**ол**г**овечн**о**сть` | 300 − штрафы |

Штраф за разрывы между совпавшими буквами, бонус за совпадение на границе
слова (после `-`, `_`, пробела, смены регистра). Ниже порога отсечения
результаты не показываются вовсе — запрос из одной буквы иначе вывалил бы весь
диск.

Три правила для русского:

- регистр не учитывается;
- **`е` и `ё` равнозначны** — в именах файлов «ё» пишут через раз;
- **нормализация в NFC** — macOS хранит имена в NFD (`й` = `и` + диакритика), и
  без этого поиск по «й» молча не находил бы ничего. Тот же класс ошибок, что
  канонизация путей в `DirectoryLoader`.

### Границы и состав файлов

По правилу проекта каждая граница с ОС — протокол.

```
SearchQuery.swift          запрос: строка, область, порог размера
SearchResult.swift         находка: URL, путь внутри архива, балл, совпавшие буквы
FuzzyMatcher.swift         сопоставление и баллы (чистая функция)
ZipCentralDirectory.swift  парсер хвоста ZIP
ArchiveListing.swift       протокол «дай оглавление» + диспетчер по формату
SearchEngine.swift         конвейер, параллелизм, отмена, кэш
SearchModel.swift          @Observable состояние для UI
```

`ArchiveListing` даёт то же, что `Mounting` и `ReleaseFetching`: движок
тестируется без единого архива на диске и без запуска процессов.

UI в `Sources/Pathway`: поле поиска, список результатов вместо файлового
списка, строка состояния с прогрессом и предупреждением о пропущенных архивах.

### Пороги

Числа заданы здесь, а не во вью: это правила, а не оформление — как порог
`isNearlyFull` в `VolumeUsage`.

| порог | значение | почему |
|---|---|---|
| размер архива на **сетевом** томе | 50 МБ | при ~9 мс на запись и чтении RAR целиком больший архив стоит секунд |
| размер архива на **локальном** диске | 500 МБ | чтение с SSD дёшево, порог нужен лишь против гигантских образов |
| записей на архив | 100 000 | защита памяти: 10 000 записей читаются за 28 мс, скорость не проблема |
| порог отсечения по баллу | 250 | ниже — только нечёткие совпадения со многими разрывами |

Пороги различаются по типу тома, потому что различается цена: `isNetwork`
известен из `VolumeUsage`/`URLResourceKey`. Один общий порог был бы либо
слишком строг для локального диска, либо разорителен для сети.

### Кэш оглавлений

В памяти, на сеанс. Ключ — путь + размер + дата изменения: изменённый архив
перечитывается, неизменённый берётся из кэша. Важно на сети, где RAR дорог.

Не на диске: инвалидация, миграции и чистка — заметно больше движущихся
частей ради выигрыша во втором запуске подряд.

## Поток данных

```
Enter в поле поиска
  ↓
SearchModel.search(query)  → отменяет прошлый Task
  ↓
SearchEngine.run
  ├ обход каталога (opendir/readdir)
  │   └ FuzzyMatcher → результаты в UI потоком
  └ архивы, прошедшие порог размера
      └ 6–8 параллельных задач
          ├ ZIP → ZipCentralDirectory (хвост, 0,03 мс)
          └ RAR/7z/tar → bsdtar -tf (весь файл)
              └ FuzzyMatcher → результаты в UI потоком
  ↓
SearchModel.results (отсортированы по баллу) + skipped + failed
  ↓
UI: плоский список, «Заказы.zip › 2024/договор.pdf»
```

## Ошибки

Текст ошибки рождается в Core, UI показывает — как везде в проекте. У поиска
особенность: **одна ошибка не валит весь поиск**.

| ситуация | поведение |
|---|---|
| архив битый | пропускаем, счётчик «не удалось прочитать N» |
| архив зашифрован | имена в ZIP/RAR не шифруются — читаем как обычно, пароль не спрашиваем |
| архив больше порога | пропускаем, показываем в списке с кнопкой «Проверить всё равно» |
| сетевой том отвалился | поиск останавливается, показывается ошибка |
| вложенный архив в архиве | не вскрываем (см. «Вне рамок») |
| свыше 100 000 записей в архиве | список обрезается, архив попадает в «пропущенные» |
| отмена | молча: `CancellationError` глотается, как в остальном проекте |

Про пароли: имена файлов в ZIP и RAR хранятся открытыми даже в зашифрованных
архивах — на этом же основан пароль-заглушка `-` в `ArchiveService`. Поиск по
именам работает и в защищённых архивах. Извлечение по двойному клику — уже
спросит пароль, через существующий `BrowserModel.passwordRequest`.

## Тесты

`FuzzyMatcherTests` — ядро чёткости:

- точное совпадение ранжируется **выше** начала слова, а не наравне;
- `дгвр` находит `Договор`, но балл **ниже**, чем у прямого `договор`;
- регистр не важен; `е` и `ё` равнозначны;
- имя в NFD (как хранит macOS) находится по запросу в NFC, **а не теряется**;
- буквы не по порядку не совпадают (`ргд` ≠ `Договор`);
- результат ниже порога отсечения не попадает в выдачу.

`ZipCentralDirectoryTests` — парсер:

- читает имена из архива, у которого испорчено всё, кроме хвоста;
- кириллица возвращается корректно, **а не заменой на `?`**;
- имя в CP437 (старый архиватор) декодируется, а не даёт мусор;
- битый хвост даёт пустой список, **а не крэш**;
- архив с 10 000 записей разбирается за разумное время.

`SearchEngineTests` — на подменённом `ArchiveListing`:

- находки из архивов и с диска попадают в один список;
- один битый архив не отменяет поиск, а увеличивает счётчик пропущенных;
- архив больше порога **не вскрывается вовсе** — проверяется тем, что
  `ArchiveListing` не был вызван;
- порог берётся по типу тома: архив на 100 МБ вскрывается на локальном диске,
  но пропускается на сетевом — **а не наоборот и не одинаково**;
- отмена прекращает работу и не шлёт результаты после неё;
- повторный поиск по той же папке **не зовёт** `ArchiveListing` второй раз;
- изменение размера или даты архива кэш инвалидирует.

## Что изменилось при реализации

Два решения разошлись с первоначальным замыслом; здесь они с причинами.

**Извлечение записи распаковывает архив целиком.** Задумывалось извлекать одну
запись отбором средствами `bsdtar`. При запуске из процесса приложения тот не
находит записи с кириллицей в имени — ни позиционным шаблоном, ни через
`--include`, ни в NFC, ни в NFD, ни с выставленным `LANG`; из shell та же
команда с теми же байтами отрабатывает. Дело в окружении процесса, а не в
кодировке, но для проекта, где файлы называются по-русски, отбор, спотыкающийся
на кириллице, негоден в принципе. Архив распаковывается во временную папку
целиком, нужный файл отбирается уже на диске. Цена ограничена сверху порогом
размера: записи ищутся среди того, что поиск уже вскрыл.

**Движок — не актор.** Первая версия была актором, и вскрытие архивов
сериализовалось: каждая задача ждала освобождения изоляции. Изменяемое
состояние здесь только кэш оглавлений, он и вынесен в отдельный актор.

Отдельно потребовалась работа над скоростью `FuzzyMatcher`. На архиве с десятью
тысячами длинных имён поиск занимал 1,8 с, и виноват был не ввод-вывод:
построение карты индексов для каждого имени с посимвольным созданием строк
стоило 154 мкс на стосимвольное имя. Дешёвый отсев по вхождению букв по порядку
до построения карты и подготовка свёртки запроса один раз на поиск дали 8 мкс —
в девятнадцать раз. На настоящей рабочей папке поиск укладывается в 1–3 мс.

## Ручной чек-лист

- [ ] Поиск по локальной папке с архивами: результаты появляются потоком,
      обычные файлы — раньше содержимого архивов.
- [ ] Файл внутри `.zip` находится; путь показан как «Архив.zip › папка/файл».
- [ ] Файл внутри `.rar` находится (RAR4 и RAR5).
- [ ] Русское имя внутри архива находится по русскому запросу — без `?`.
- [ ] Имя с «ё» находится по запросу с «е» и наоборот.
- [ ] Двойной клик по записи из архива извлекает файл и открывает его.
- [ ] Enter запускает поиск; Esc закрывает и возвращает список файлов.
- [ ] Поиск на сетевом томе (FTP/SMB) не вешает интерфейс.
- [ ] Архив больше порога попадает в «пропущенные»; «Проверить всё равно»
      вскрывает его.
- [ ] Смена папки или новый запрос отменяет прошлый поиск без ошибок.
- [ ] Зашифрованный архив: имена находятся, пароль не спрашивается.

## Вне рамок

- **Поиск по содержимому файлов внутри архивов.** Требует распаковки каждого
  файла в память; архитектура конвейера это допускает вторым шагом без
  переделки, но в текущий объём не входит.
- **Вложенные архивы (архив в архиве).** Рекурсия требует извлечения
  промежуточного архива на диск — другая цена и другая модель отмены.
- **Индекс на диске между запусками.** Инвалидация, миграции и чистка — больше
  движущихся частей, чем выигрыш во втором запуске подряд.
- **Поиск по всему диску как режим по умолчанию.** Область — текущая папка;
  переключатель «искать везде» может появиться позже.
- **Маски `*` и `?`.** Выбрано нечёткое сопоставление; два режима в одной
  строке дали бы много краевых случаев.
- **Установка сторонних архиваторов** (`unar`, `7z`, `unrar`) ради форматов,
  которых не знает libarchive. Приложение раздаётся коллегам вручную, требовать
  установки утилит нельзя.
