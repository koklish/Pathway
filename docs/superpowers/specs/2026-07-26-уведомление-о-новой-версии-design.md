# Уведомление о новой версии при запуске

## Цель

Проверка обновлений при запуске уже вызывается, но узнать о найденной версии почти невозможно:
результат виден одной синей точкой шести пикселей в правом углу строки заголовка. Коллега,
не знающий, что там что-то появляется, не заметит её никогда.

Вторая беда — сама проверка на старте срабатывает не всегда. `checkAutomatically()` начинается
с `guard shouldCheckNow`, и если проверка уже случилась в течение суток, запуск приложения GitHub
не спрашивает вовсе. «Включил приложение — узнал о новой версии» сегодня не работает.

Нужно: проверять при каждом запуске и показывать системное уведомление macOS со звуком, по клику
открывающее поповер версии с заметками к выпуску и кнопкой загрузки.

## Архитектура

### Частота: `checkOnLaunch` рядом с `checkAutomatically`

`Sources/PathwayCore/UpdateService.swift`

Суточное ограничение снимается с пути запуска, но остаётся в сервисе:

- **`checkOnLaunch()`** — без ограничений. Старт процесса случается редко, и человек в этот момент
  явно ждёт свежих данных.
- **`checkAutomatically()`** — прежнее поведение с `shouldCheckNow`. Сейчас её не зовёт никто, кроме
  тестов; она остаётся ради будущих периодических проверок, где лимит GitHub (60 запросов в час на
  адрес, а все коллеги могут сидеть за одним NAT) снова станет важен.

Выбрано вместо простого удаления `shouldCheckNow`: удаление оставило бы поле `lastCheck` — его
показывает подвал поповера строкой «Проверено в 21:59» — записываемым, но ни на что не влияющим,
а защиту от лимита пришлось бы писать заново при первой же фоновой проверке.

### Граница с ОС: протокол `UpdateNotifying`

`Sources/PathwayCore/UpdateNotifier.swift` — новый файл.

`UserNotifications` — очередная граница с системой, и вводится она тем же приёмом, что `Mounting`,
`CredentialStoring`, `TerminalRunning`, `AppTerminating`:

```swift
public protocol UpdateNotifying: Sendable {
    func requestAuthorization() async
    func notify(about release: ReleaseInfo) async
}
```

Ни один метод не бросает — намеренно, см. раздел «Ошибки».

**`SystemUpdateNotifier`** — боевая реализация поверх `UNUserNotificationCenter`:

- Заголовок «Доступна версия 1.2.0», тело — первая строка заметок к выпуску через существующий
  `ReleaseNotes.sections(_:after:)`, либо «Нажмите, чтобы посмотреть, что изменилось», если заметок
  нет.
- Звук `UNNotificationSound.default`: подчиняется системным настройкам и режиму «Не беспокоить»,
  в отличие от собственного файла.
- `interruptionLevel = .active`.
- Идентификатор запроса — `"update-<версия>"`. Повторный баннер про ту же версию **заменяет** прежний
  в Центре уведомлений, а не копится стопкой: уведомлять решено при каждом запуске, и без общего
  идентификатора десять запусков дали бы десять одинаковых строк — это мусор, а не напоминание.
- **`guard Bundle.main.bundleIdentifier != nil`** в начале обоих методов. При `swift run` приложение
  выполняется не из бандла, и `UNUserNotificationCenter.current()` в этом случае бросает исключение —
  без проверки отладочный запуск падал бы на старте.

Файл импортирует `UserNotifications` в Core. Это не нарушение границы: правило звучит как «нет типов,
которые рисуют», а не «нет AppKit» — ровно по той же причине в Core уже живут `NSWorkspace`,
`NSPasteboard` и `NSAppleScript`. SwiftUI по-прежнему в Core нет нигде.

### Кто решает, что пора уведомить

Единственная точка — переход в `.available` внутри `check`:

```swift
guard let release, release.version > currentVersion else {
    state = .upToDate
    return
}
state = .available(release)
if notifyOnFind { await notifier.notify(about: release) }
```

`notifyOnFind` — параметр `check`, а не поле сервиса. Поднят у `checkOnLaunch()` и
`checkAutomatically()`, опущен у `checkManually()`: нажавший «Проверить сейчас» смотрит в открытый
поповер, и системный баннер поверх него уведомлял бы о том, что человек видит своими глазами.

`await` перед `notify`, а не `Task { }` без ожидания: последнее превратило бы тест «уведомил про
найденную версию» в гонку. Задержки на глаз нет — `UNUserNotificationCenter.add` возвращается сразу,
доставка асинхронна внутри системы.

Разрешение сервис не запрашивает сам никогда — только показывает. `requestNotificationAuthorization()`
на `UpdateService` есть, но это тонкая обёртка над нотификатором, и зовёт её делегат приложения.

### Обратный канал: клик по баннеру → поповер

Приём тот же, что у `AppState.pendingRename` и `BrowserModel.passwordRequest`: Core выставляет
запрос, вью его исполняет и сбрасывает.

**`UpdateService.showPopoverRequest: Bool`** — наблюдаемое свойство. Живёт в сервисе, а не в
`AppState`: делегат приложения уже держит ссылку на `updates`, а до `AppState` ему тянуться неоткуда —
он получает только `onboarding`. И состояние это про обновления, а не про браузер файлов.

`Bool`, а не счётчик: повторный клик по баннеру при уже открытом поповере ничего делать не должен,
и сброс в момент показа даёт это даром.

**`PathwayAppDelegate`** становится `UNUserNotificationCenterDelegate` и ставит себя делегатом Центра
в `applicationDidFinishLaunching` — обязательно до первого показа, иначе клик по баннеру не дойдёт
ни до кого.

Два метода делегата:

- **`didReceive`** (клик) — `NSApp.activate()` (приложение могло быть свёрнуто) и подъём
  `showPopoverRequest`.
- **`willPresent`** — возвращает `[.banner, .sound]`. Без него баннер не показывается вовсе, пока
  приложение активно: macOS по умолчанию глотает уведомления собственного активного приложения,
  и весь смысл пропадал бы именно в самом частом случае — приложение только что запустилось и оно
  на переднем плане.

**`BadgeChipHost`** (`Sources/Pathway/UpdateBadgeView.swift`) получает в `Coordinator` метод
`showPopover(from:)` — открыть, если ещё не открыт, — а в `updateNSView` проверку флага. Отдельный
метод, а не переиспользование `togglePopover`: `toggle` при уже открытом поповере его бы закрыл,
и клик по баннеру гасил бы то, что должен показать.

### Разрешение при первом запуске

`PathwayAppDelegate.applicationDidFinishLaunching`:

```swift
BundleUpdateInstaller.cleanUpAfterUpdate()
Task { @MainActor in
    await updates?.requestNotificationAuthorization()
    await updates?.checkOnLaunch()
}
MainActor.assumeIsolated { onboarding?.startIfFirstLaunch() }
```

Порядок внутри `Task` существен: сначала разрешение, потом проверка. Иначе на первом запуске проверка
успела бы найти версию и попытаться показать баннер раньше, чем разрешение вообще запрошено, —
и первое уведомление потерялось бы молча.

Своего флага «первый запуск» нет. `UNUserNotificationCenter.requestAuthorization` показывает системный
диалог ровно один раз, а при повторных вызовах молча возвращает принятое ранее решение без всякого UI.
Флаг в `UserDefaults` был бы вторым источником правды о том, что система и так помнит, и разошёлся бы
с ней при сбросе разрешений в Настройках. Запрос идёт при каждом запуске, диалог человек видит один раз.

## Поток данных

```
applicationDidFinishLaunching
  → updates.requestNotificationAuthorization()   → notifier.requestAuthorization()
  → updates.checkOnLaunch()                      → check(silent: true, notifyOnFind: true)
      → fetcher.latestRelease()
      → version > currentVersion?
          нет → state = .upToDate                (тишина)
          да  → state = .available(release)      (синяя точка на чипе)
              → notifier.notify(about: release)  (баннер + звук)

клик по баннеру
  → PathwayAppDelegate.userNotificationCenter(_:didReceive:)
      → NSApp.activate()
      → updates.showPopoverRequest = true
          → BadgeChipHost.updateNSView видит флаг
              → Coordinator.showPopover(from:)
              → updates.showPopoverRequest = false
```

## Ошибки

Уведомления — не тот канал, где стоит беспокоить человека. Ни отказ в разрешении, ни сбой
`UNUserNotificationCenter.add` не попадают ни в `errorMessage`, ни в `UpdateState.failed`:
обновление доступно независимо от того, показался баннер или нет, а синяя точка на чипе работает
всегда.

`SystemUpdateNotifier` глотает свои ошибки внутри себя, и его методы не бросают. Это видно прямо
в сигнатуре протокола (`async` без `throws`) — забыть обработать нечего, потому что обрабатывать
нечего по типу.

## Тесты

`Tests/PathwayCoreTests/UpdateNotifierTests.swift` плюс дополнения к `UpdateServiceTests.swift`.
Двойник `SpyNotifier` считает запросы разрешения и запоминает релизы, про которые уведомляли;
настоящий `UNUserNotificationCenter` в тестовом процессе не трогается вовсе — приложение там
выполняется не из бандла.

1. `checkOnLaunch` спрашивает GitHub, даже если проверка была минуту назад
2. `checkAutomatically` по-прежнему молчит в пределах суток — старое поведение не сломано
3. нашли версию новее → нотификатор получил ровно один вызов, и именно с этим релизом
4. версия та же или старее → нотификатор не звали вовсе
5. `checkManually` нашла новую версию → баннер не показан: человек смотрит в поповер
6. проверка упала с ошибкой сети → нотификатор не звали
7. `requestNotificationAuthorization` доходит до нотификатора
8. клик по уведомлению поднимает `showPopoverRequest`, показ поповера его сбрасывает
9. второй запуск с той же доступной версией снова уведомляет — «каждый запуск» зафиксирован тестом,
   иначе это легко «оптимизировать» обратно в «один раз на версию»

## Ручной чек-лист

Уведомления не проверяются тестами — нужен настоящий подписанный бандл.

- [ ] Собрать бандл, стереть разрешение (`tccutil reset Notifications com.pathway.filemanager`),
      запустить → системный диалог про уведомления появился один раз
- [ ] При доступном обновлении запустить приложение → баннер со звуком, приложение при этом
      на переднем плане (проверяет `willPresent`)
- [ ] Клик по баннеру при свёрнутом окне → окно вышло вперёд, поповер раскрыт
- [ ] Отказать в разрешении → приложение работает, синяя точка на чипе на месте
- [ ] `swift run` без бандла → не падает, просто без уведомлений
- [ ] Перезапустить дважды подряд, не обновляясь → баннер оба раза, в Центре уведомлений одна
      строка, а не две
- [ ] Нажать «Проверить сейчас» в поповере при доступном обновлении → баннера нет

## Вне рамок

- **Настройка «не уведомлять» внутри приложения** — системных настроек уведомлений macOS достаточно,
  своя копия переключателя разошлась бы с ними.
- **Кнопки-действия на самом баннере** («Обновить» прямо из уведомления) — требуют категории действий
  и заметно больше кода ради шага, который человек всё равно делает в поповере, увидев заметки.
- **Уведомление о завершённой загрузке** — загрузку человек запускает сам и смотрит на её прогресс
  в поповере.
- **Фоновая проверка по таймеру во время работы приложения** — `checkAutomatically()` для этого
  остаётся готовой, но таймера сейчас нет и он не нужен: приложение перезапускают достаточно часто.
- **Собственный звуковой файл** — выбивался бы из системного звучания и не подчинялся бы настройкам.
