# «Найти» в пакетном переименовании как фильтр набора

## Цель

Выделены четыре объекта: «3Новая», «4Новая 2», «5пывпыва», «2123». В поле
«Найти» введено «Новая», «Заменить на» пусто. Сейчас план выглядит так:

```
3Новая     → 3
4Новая  2  → 4  2
5пывпыва   → 5пывпыва
2123       → 2123
```

и внизу написано «Будет переименовано: 4». Два последних объекта в
переименовании не участвуют по смыслу — их имя не меняется, — но входят в
план, считаются в счётчике и занимают номер при нумерации.

Ожидание другое: **«Найти» отбирает файлы, к которым правило применяется**.
Не совпал — файла в плане нет вовсе, ни в превью, ни в счётчике, ни в
нумерации. Совпал — применяются все остальные правила: замена (в том числе
на пустоту — это осознанное удаление подстроки), регистр,
префикс/суффикс, нумерация.

Цель — сделать «Найти» фильтром набора, оставив семантику самой замены
прежней.

## Архитектура

### Отбор в `BatchRenamePlan.build`

`Sources/PathwayCore/BatchRename.swift`

`build` получает те же `items`, но перед построением шагов отсеивает
элементы, чьё имя **без расширения** не содержит `rule.find` (с тем же
флагом `caseSensitive`, что и у замены). Пустое `find` не фильтрует ничего:
правило «префикс ко всем выделенным» должно продолжать работать.

Сравнение идёт по имени без расширения — по тому же тексту, к которому
применяется замена. Иначе «Найти: jpg» отобрало бы файлы, в которых менять
нечего: замена работает по базе, а фильтр — по полному имени, и в превью
получилось бы «отобран, но не изменился».

**Фильтр применяется до нумерации, а не после.** Номер = позиция в
отфильтрованном массиве, поэтому «Найти: Новая» + нумерация даёт 1, 2 у двух
подходящих, а не 1, 2 через дырки на месте отсеянных. Считать номера по
исходному массиву значило бы показывать в превью пропуски, которых человек
не задавал.

Никаких новых полей в `BatchRenameRule` не появляется: фильтр — следствие
уже существующего `find`, а не отдельный режим. Второй флаг («find как
фильтр / как замена») означал бы два поведения одного поля и вопрос «какое
из них у меня сейчас» в каждом открытии листа.

### Следствие для конфликтов и исполнения

Меняется только состав входного набора; логика конфликтов и двухпроходного
исполнения не трогается. Одно уточнение по конфликту «имя занято на диске»:
множество `sources` собирается **по отфильтрованным** элементам, а не по
всем поданным. Файл, отсеянный фильтром, никуда не уедет — значит его имя
занято по-настоящему, и цель, совпавшая с ним, обязана быть конфликтом.
Собирай `sources` по всем поданным items, и переименование «в имя
невыделенного-но-поданного» прошло бы молча с потерей файла.

### Счётчик в листе

`Sources/Pathway/BatchRenameSheet.swift`

Строка «Будет переименовано: N» уже считает по `steps`, поэтому отдельной
правки не требует — после фильтрации `steps` короче, и число само станет
верным. Добавляется только пояснение под заголовком, когда фильтр что-то
отсеял: «Объектов: 4, подходит: 2» — иначе исчезновение строк из превью
выглядело бы как потеря выделения.

### Подсказка у поля

Поле «Найти» получает `help` (тултип): «Отбирает объекты, содержащие этот
текст. Пустое «Заменить на» удаляет найденное». Пустое «Заменить на» как
удаление — не баг, а нормальный сценарий, и объяснить его надо там, где
человек смотрит.

## Поток данных

```
items (выделение) + rule
  ↓
BatchRenamePlan.build
  matched = find.isEmpty ? items : items.filter { база содержит find }
  ↓
  шаги строятся по matched, index — позиция в matched (нумерация)
  ↓
  конфликты: sources — пути matched, а не всех items
  ↓
[RenameStep] → превью, счётчик, исполнение (без изменений)
```

## Тесты

`Tests/PathwayCoreTests/BatchRenameTests.swift`, тот же сьют:

- **«Найти» отбирает набор: не совпавшие в план не попадают** — items
  «3Новая», «5пывпыва»; find «Новая» → один шаг, и он про «3Новая».
- **отбор регистронезависим по умолчанию и учитывает регистр по флагу** —
  find «новая» ловит «3Новая»; с caseSensitive не ловит.
- **пустое «Найти» не фильтрует ничего** — только префикс, оба элемента в
  плане (защита от «фильтр отсёк всё при пустом поле»).
- **отбор идёт по имени без расширения, а не по полному имени** — файл
  «a.jpg», find «jpg» → ноль шагов: менять в базе нечего.
- **нумерация считается по отфильтрованному набору, а не по исходному** —
  items «x1», «нет», «x2»; find «x» + нумерация-суффикс → «x11», «x22», без
  пропуска номера на отсеянном.
- **цель, совпавшая с именем отсеянного файла, — конфликт** — items «a.txt»
  (совпал) и «c.txt» (не совпал, остаётся на месте); замена делает из «a»
  «c» → конфликт «имя занято», а не молчаливая перезапись.
- существующие тесты сьюта остаются и должны проходить: у них либо пустое
  `find`, либо `find`, совпадающий со всеми поданными элементами. Проверить
  каждый — там, где ожидалось «не совпал → остаётся с прежним именем»
  (`replacementRespectsCaseWhenAsked`), ожидание меняется на «не совпал →
  выпал из плана».

## Вне рамок

- **Отдельный флаг «find как фильтр / как замена».** Два поведения одного
  поля и вопрос «какое сейчас» при каждом открытии листа; выбранная
  семантика — одна и всегда.
- **Показ отсеянных серыми строками в превью.** Строка «не будет
  переименован» в таблице результатов — шум: у неё нет нового имени, и
  красный конфликт от серого пропуска отличать пришлось бы глазами.
  Количество отсеянных названо числом в подписи.
- **Фильтр по расширению или маске (`*.jpg`).** Второй синтаксис отбора
  поверх подстроки; отбор по типу делается выделением в списке до открытия
  листа.
