# Пакетное переименование с живым превью

## Цель

Выделены двадцать фотографий «IMG_4021.jpg…» — и их хочется назвать
«Отпуск 01.jpg…». Инлайн-переименование делает это по одному файлу, а
сторонняя утилита — выход из приложения. В Проводнике Windows пакетного
переименования тоже нет (только «имя (N)»), но ожидание сформировано
Total Commander и Finder-автоматизациями.

Цель — **лист пакетного переименования**: правила (найти/заменить,
префикс/суффикс, нумерация, регистр) и таблица превью «старое имя → новое
имя», пересчитываемая на каждое изменение полей. Конфликты видны до
выполнения и подсвечены красным.

## Архитектура

### Движок: `BatchRenameRule` и `BatchRenamePlan`

`Sources/PathwayCore/BatchRename.swift` (новый файл)

`BatchRenameRule` — структура-значение со всеми полями правил: find/replace
с флагом caseSensitive, prefix/suffix, нумерация (режим off/prefix/suffix,
start, step, pad), changeCase (none/lower/upper/title). Структура, а не
цепочка отдельных операций: набор правил фиксирован, и лист редактирует её
по полям напрямую, без пересборки массива.

Чистый `BatchRenamePlan.build(items:rule:) -> [RenameStep]` — без побочных
эффектов, отсюда тестируемость и живое превью «на каждый keystroke».
Шаг: `(item, newName, status)`, статус `.ok` или `.conflict(причина)`.

Все правила применяются к имени **без расширения**, расширение сохраняется
всегда: «замена IMG → Отпуск в IMG_4021.jpg» не должна превращать файл в
«Отпуск» без типа. Порядок применения фиксирован: замена → регистр →
префикс/суффикс → нумерация. Именно так, а не «в порядке полей листа»:
нумерация обязана видеть финальное имя, иначе «Отпуск 01» превратился бы в
«01 Отпуск» при суффиксе, применённом после номера.

Порядок нумерации = порядок входного массива. В UI массив — это
`BrowserModel.selectedItems`, то есть текущая сортировка списка: человек
видит превью ровно в том порядке, в котором пойдут номера.

Пустое правило (все поля по умолчанию) даёт ноль шагов, а не план
«переименовать всё в то же имя»: без него кнопка «Переименовать» была бы
активна на пустом листе, и нажатие ничего бы не делало.

### Конфликты — до выполнения, а не по ходу

Три вида, все вычисляются в `build`:

- имя занято существующим файлом на диске (проверка `FileManager` по папке
  каждого элемента). Имена других переименовываемых источников занятыми
  **не считаются**: они к моменту записи цели уже уедут на своё новое имя,
  и считать их занятыми запрещало бы законный обмен a↔b;
- два результата совпали друг с другом;
- пустое имя или имя с «/»/«:».

Конфликт — данные плана, а не исключение в момент записи: лист показывает
причину красным до нажатия кнопки, а конфликтные строки просто пропускаются
при выполнении. Проверка «на диске», а не «по списку items»: файл с тем же
именем мог лежать вне выделения или появиться после построения списка.

### Исполнение в два прохода: `BatchRenameExecutor`

Если множество целевых имён пересекается со множеством исходных (обмен
a↔b, сдвиг нумерации), прямой проход затёр бы файл, чьё имя ещё нужно
другому шагу. Поэтому при пересечении: сначала все источники → временные
уникальные имена (`.pathway-rename-<uuid>-<n>`) в той же папке, затем →
целевые. Без пересечения — один проход, временные имена не нужны.

Запись — через `FileOperations.rename` (переименование = move в той же
папке), а не свой `moveItem`: там уже валидация имени и проверка занятости,
и инвалидацию кэша/перечитывание сделает `BrowserModel.run` наверху, как у
всех файловых операций.

Ошибка посередине (файл исчез, диск отвалился) не прерывает пакет: шаг
помечается неудавшимся, выполнение продолжается, итог — сводка
«переименовано N из M, не удалось: …». Прерывать весь пакет из-за одного
файла значило бы оставить половину файлов переименованными без объяснения,
какие именно.

### Команда и pending-запрос

`Sources/PathwayCore/Commands.swift`, `AppState.swift`

`CommandID.batchRename` — «Переименовать выбранные…», шорткат ⌃⌘R.
Не ⇧⌘R: тот занят «Показать в Finder», и тест «шорткаты не конфликтуют»
ловит такие дубли. ⌃⌘R свободно и стандартным пунктом «Правки» не занято,
перехватывать у текстовых полей нечего. Доступность: не редактируется
текст, том не read-only, выделено ≥ 2 элементов (для одного есть F2 —
инлайн-редактор удобнее листа). Команда в `writesToDisk`.

Действие — pending-паттерн: `AppState.pendingBatchRename = [FileItem]`,
UI открывает лист и сбрасывает, как `pendingCompress`. Прямого выполнения в
команде нет — листу нужен UI.

### Лист: `BatchRenameSheet`

`Sources/Pathway/BatchRenameSheet.swift` (новый файл)

Сверху блок правил (найти/заменить + регистронезависимость, префикс,
суффикс, нумерация: режим/начало/шаг/разряды, регистр), снизу таблица
превью «старое имя → новое имя». Превью — `BatchRenamePlan.build` от
текущих полей, пересчёт на каждое изменение: движок чистый и дешёвый,
дебаунс не нужен. Конфликтные строки красные, с текстом причины, при
выполнении пропускаются.

Кнопка «Переименовать» активна, пока есть ≥ 1 шаг `.ok` — иначе нажатие
было бы молчаливым ничегонеделанием. `isEditingText` поднимается через
уже существующий `.modalTextEditing(appState)` — сброс на `.onDisappear`,
а не на кнопках: Esc закрывает лист мимо них.

Выполнение — `BrowserModel.applyBatchRename(steps:)`: исполнитель +
перечитывание списка; сводка с неудачами — в `BrowserModel.errorMessage`,
тот же канал, что у остальных файловых операций, а не отдельный алерт в
листе: лист к этому моменту уже закрыт, и тексту больше некуда уйти.

Подключение — в `MainWindow` рядом с `.sheet` для `pendingCompress`, по
тому же образцу.

## Поток данных

```
Выделение ≥ 2 → ⌃⌘R / меню «Файл» / контекстное меню
  ↓
CommandRegistry[.batchRename].run → appState.pendingBatchRename = selectedItems
  ↓
MainWindow .sheet → BatchRenameSheet(items)
  поля редактируют @State rule
    ↓ (каждое изменение)
  BatchRenamePlan.build(items, rule) → [RenameStep] → таблица превью
  ↓ «Переименовать»
model.applyBatchRename(steps.filter(.ok))
  executor: два прохода при пересечении имён, иначе один
  FileOperations.rename по шагам, ошибки собираются в сводку
  ↓
cache.invalidate + reload; неудачи → errorMessage
appState.pendingBatchRename = nil
```

## Тесты

`Tests/PathwayCoreTests/BatchRenameTests.swift`, сьют «Пакетное переименование»:

- **замена находит подстроку без учёта регистра по умолчанию** — find
  «img» меняет и «IMG_1», и «img_2».
- **замена с учётом регистра не трогает другое написание** — caseSensitive:
  «IMG_1» меняется, «img_2» остаётся.
- **замена не трогает расширение, а не переписывает имя целиком** —
  «IMG_1.jpg» → «Фото_1.jpg», не «Фото_1» и не «Фото_1.JPG».
- **префикс и суффикс добавляются к имени без расширения** — «a.txt» →
  «[a]1.txt» при prefix «[», suffix «]1»... (конкретнее: prefix «x-»,
  suffix «-y» → «x-a-y.txt»).
- **нумерация-префикс с паддингом и шагом** — start 5, step 5, pad 3 →
  «005-a.txt», «010-b.txt».
- **нумерация-суффикс идёт после остальных правил, а не до** — замена +
  суффикс-нумерация даёт «Отпуск-1.jpg», не «1-Отпуск.jpg».
- **порядок нумерации совпадает с порядком входного массива, а не с
  сортировкой имён** — подать элементы «b, a» → номера 1, 2 в этом порядке.
- **смена регистра применяется к имени без расширения** — upper:
  «Ab.txt» → «AB.txt».
- **комбинация правил применяется в фиксированном порядке** — замена +
  префикс + нумерация на одном наборе.
- **пустое правило даёт ноль шагов** — иначе кнопка была бы активна на
  пустом листе.
- **конфликт: имя занято файлом вне выделения** — на диске «c.txt» не
  выделен; результат шага «c.txt» → .conflict.
- **имя переименовываемого источника занятым не считается** — обмен a↔b
  не даёт конфликта «имя занято».
- **конфликт: два результата совпали** — два файла → одно имя, оба шага
  .conflict.
- **конфликт: недопустимое имя** — replace даёт «» или имя с «/» →
  .conflict с причиной.
- **обмен имён a↔b выполняется на диске, а не теряет файл** — withTempDir,
  два файла, plan, execute; после — оба существуют с обменянным
  содержимым.
- **без пересечения имён временные файлы не создаются** — после execute в
  папке нет файлов «.pathway-rename-*».
- **ошибка посередине пропускает шаг, а не прерывает пакет** — удалить
  один источник между build и execute; остальные переименованы, сводка
  «N из M» с именем неудавшегося.
- **команда доступна при выделении ≥ 2 и недоступна при одном** — в
  CommandsTests или здесь через AppState: isEnabled от количества
  выделенного, run выставляет pendingBatchRename.

## Ручной чек-лист

- [ ] Выделить ≥ 2 файлов → ⌃⌘R → лист с превью.
- [ ] Ввод в «Найти»: превью меняется на каждый символ.
- [ ] Конфликт с существующим файлом: строка красная, причина видна,
      кнопка активна, файл пропущен.
- [ ] Обмен имён a↔b через замену: оба файла на месте, содержимое не
      потеряно.
- [ ] Во время листа F2/⌘⌫ не срабатывают под ним (isEditingText).
- [ ] Частичная неудача (файл заблокирован): алерт со сводкой после
      закрытия листа.
- [ ] Пункт есть в меню «Файл» и в контекстном меню при ≥ 2 выделенных.

## Вне рамок

- **Регулярные выражения в «Найти».** Второй синтаксис со своими ошибками
  («невалидный паттерн» — новый вид состояния в листе) ради редкой
  мощности; подстрока покрывает основной сценарий.
- **Откат пакета.** Потребовал бы журнала операций, которого в проекте нет
  вообще (undo нет и у обычного переименования); превью и есть защита.
- **Ручной порядок нумерации (перетаскивание строк превью).** Своя
  модель порядка поверх сортировки списка — второй источник правды;
  желаемый порядок задаётся сортировкой списка до открытия листа.
- **Переименование между папками (правила с путями).** Это уже
  перемещение со своими конфликтами и инвалидацией двух папок; задача
  про имена в одной папке.
